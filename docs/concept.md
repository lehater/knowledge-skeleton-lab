# Knowledge Skeleton Lab — концепция и пользовательский сценарий

**Статус:** описание экспериментальной идеи и ожидаемого поведения, **не** результат выполненного Discovery и **не** замена нормативным правилам. Действующий кандидатный контракт задаётся в [rules/](../rules/README.md), первый пилот — в [brief](../experiments/asynchronous-programming/brief.md).

## 1. Идея

Агент получает **границы предметной области** и строит её **семантический каркас**: перечень самостоятельных знаний, граф предметных категорий и обоснованные типизированные связи. Сначала создаются Markdown-файлы **только с YAML frontmatter и заголовком H1**. Объясняющий материал добавляется позже, уже к проверенным узлам.

Проблема, которую решаем: создание заметок сразу с длинными объяснениями затрудняет обзор предметной области, выявление пропусков и дубликатов. Каркас позволяет **сначала исследовать структуру**, а затем постепенно наполнять её знаниями без изменения устойчивой идентичности узлов.

**Предположение эксперимента:** ограниченный Discovery + независимое ревью позволят получить пригодную к навигации структуру быстрее, чем полное ручное создание и написание всех заметок. Это **гипотеза**, а не доказанный результат.

## 2. Сущности и ответственность

| Сущность | Ответственность | Вход → выход |
| --- | --- | --- |
| Предметная область / Scope | Границы исследования и опорные темы | Задача и источники → `experiments/.../brief.md`, baseline для проверки покрытия |
| Category | Объединяет предметы по тематической принадлежности | Категория + более широкие категории → узел `vault/taxonomy/categories/*.md` с `broader` |
| Knowledge | Представляет **один самостоятельный предмет знания** | Референт + источники → узел `vault/knowledge/entries/*.md` с `categories` и, при необходимости, типизированными отношениями |
| Typed relation | Утверждает конкретный смысл между узлами | Source, predicate, target + обоснование → одна направленная YAML-ссылка |
| Review | Проверяет смысл узлов и отношений относительно источников | Граф + независимый baseline → замечания, решение по кандидатам |
| Enrichment | Добавляет объяснения после принятия каркаса | Проверенный Knowledge → содержательный Markdown с сохранением `id` |

**`type`** различает `category` и `knowledge`. Необязательный **`kind`** описывает предметную форму Knowledge (`mechanism`, `model`, `property` и т. д.), а не тип заметки. `review_status` отвечает за проверенность узла, `lifecycle` — за наличие объяснительного содержания. Эти статусы независимы.

Категория — **не** автоматически Knowledge, а поле `broader` — **не** предметное `part_of`. На этом разделении строится согласованность графа.

## 3. Пример: Asynchronous Programming

**Вход:** «Построй каркас Asynchronous Programming, опираясь на официальные материалы Python, Rust, Kotlin и .NET; не более 30 Knowledge; пока без текстовых объяснений».

Агент исследует источники, формирует предварительные самостоятельные референты (например: `Coroutine`, `Task`, `Future`, `Cancellation`, `Cooperative Scheduling`) и группирует их по небольшому числу категорий.

### 3.1. Условная схема

~~~text
                Concurrent Programming             (category)
                         ▲
                         │ broader
              Asynchronous Programming              (category)
                    ▲            ▲
                    │            │
              Async Scheduling   Async Lifecycle     (category)
                    ▲            ▲
             categories          categories
                    │            │
                  Task        Cancellation           (knowledge)

Coroutine ──categories──▶ Asynchronous Programming
Cooperative Scheduling ──specializes──▶ Scheduling  (knowledge → knowledge)
~~~

Стрелка `broader` хранится **от более узкой категории к широкой**. Стрелка `categories` — **от Knowledge к категории**. Предметное `specializes` означает «частный вид → общий вид», а не просто тематическую близость. Другие предикаты могут иметь свою собственную семантику; **универсального направления "всегда от конкретного к общему" нет**.

Схема показывает возможную организацию, **не утверждает** семантическую корректность каждой пары до ревью.

### 3.2. Пример категории

`vault/taxonomy/categories/async-scheduling.md`:

~~~yaml
---
id: 019a0000-0000-7000-8000-000000000011
type: category
name: "Async Scheduling"
review_status: proposed
broader:
  - "[[taxonomy/categories/asynchronous-programming]]"
---
# Async Scheduling
~~~

### 3.3. Пример Knowledge

`vault/knowledge/entries/task.md`:

~~~yaml
---
id: 019a0000-0000-7000-8000-000000000012
type: knowledge
name: "Task"
kind: construct
lifecycle: skeleton
review_status: proposed
categories:
  - "[[taxonomy/categories/async-scheduling]]"
---
# Task
~~~

`id` здесь **иллюстративный**, новый ID в реальной работе создаёт `node tools/new-id.mjs`. Внутри `vault/` пока **нет** этих демонстрационных заметок: они приведены только в документации, чтобы не загрязнять эксперимент.

Из `Task → categories: Async Scheduling` и `Async Scheduling → broader: Asynchronous Programming` можно вычислить, что `Task` относится и к `Asynchronous Programming`. Повторно записывать `Asynchronous Programming` в поле `categories` необязательно.

Категория может иметь **несколько более широких родителей**. Такой граф — DAG, а не обязательно дерево. Родителей храним непосредственно; обратные связи и предков вычисляем, не дублируем.

## 4. Полный цикл работы

| Этап | Ответственность агента / проверяющего | Формируемый результат |
| --- | --- | --- |
| D0 — Scope | Определить границы `in/out`, источники и независимые контрольные темы | Воспроизводимая постановка |
| D1 — Inventory | Проверить существующие узлы, имена, `aliases` и дубли | Список повторно используемых референтов |
| D2 — Taxonomy | Создать минимальные категории и `broader` | Кандидатный DAG категорий |
| D3 — Discovery | Выделить самостоятельные знания, создать YAML + H1 | Кандидатные Knowledge со стабильными `id` |
| D4 — Relationships | Проверить и добавить прямые `categories`, `specializes`, `part_of`, `realizes` | Кандидатный предметный граф |
| D5 — Validation & Review | Проверить целостность ссылок и отдельно предметную семантику | Машинный результат + независимый отчёт |
| D6 — Enrichment (позднее) | Добавить определения, объяснения, примеры и источники к принятым узлам | Содержательные Knowledge при сохранённом `id` |

Неуверенные узлы и связи фиксируются в `reports/`, а **не** выдаются за принятые факты. Все новые узлы первого прогона имеют `review_status: proposed`, Knowledge — `lifecycle: skeleton`.

Независимый Review — это самостоятельная проверка относительно предметных источников и baseline; повторное чтение агентом собственных выводов ещё не делает ревью независимым.

## 5. Что можно делать с готовым каркасом

### Навигация

- «Какие знания относятся к `Asynchronous Programming`?» — найти все Knowledge, прямо привязанные к категории **или к её потомкам** по `broader`.
- «В каких областях встречается `Cancellation`?» — посмотреть прямые `categories` и вычисленных предков.
- «Какие частные виды `Scheduling` существуют?» — найти входящие отношения `specializes`.
- «Какие реализации абстракции известны?» — найти входящие отношения `realizes`.
- «Какие понятия ещё не наполнены?» — отобрать `lifecycle: skeleton`.
- «Что ещё не проверено?» — отобрать `review_status: proposed`.

### Представления

- **Таблицы:** встроенные Obsidian Bases в `vault/views/` для прямой фильтрации по свойствам, категориям и статусам.
- **Граф:** Obsidian Graph/Backlinks показывает структуру ссылок; типизированные отношения можно визуализировать поддерживающими YAML-ссылки плагинами (после их установки и настройки).
- **Дерево/подграф категории:** представление «категория → потомки → Knowledge», включая множества пересечений. Это **целевой пользовательский сценарий**; готовой автоматической рекурсивной проекции в текущем наборе `views/` пока нет.
- **Метрики:** числа узлов по веткам, пересечения областей, пустые категории, неподтверждённые узлы и связи. Реализация вычислений — будущая итерация по доказанной пользе.

**Важно:** число заметок в категории характеризует **наполнение Vault**, а не объективную полноту предметной области.

**Проверено в GUI 31.10.2026:** [K-Plex Graph Lenses](../reports/k-plex-lenses-pilot.md) фильтрует локальные предметные связи и сохраняет выбранные типы при переходе между Knowledge. Для **Canvas** целевой сценарий иной: целостная схема технологии и каскадная навигация по компонентам, без требования фильтрации рёбер внутри Canvas.

### Подтверждённая ценность: технологические и семантические представления

Пользователь подтвердил полезность Canvas, на котором показана **конкретная технология** (первый пример: Python `asyncio`) вместе с общими концепциями, которые реализуют её сущности. Целевое поведение — **один граф знаний, несколько независимых представлений**: по технологиям и по семействам предметных отношений.

Для точек зрения используются семейства предикатов: функциональные, реализационные, структурные и классификационные. Семейство служит **фильтром отображения**, конкретный предикат сохраняет точный предметный смысл. Целевой интерфейс позволяет показывать/скрывать выбранные отношения и отличать их цветом. **Фильтр и генерация Canvas из YAML ещё не реализованы.**

Зафиксированное архитектурное решение, границы и минимальный следующий шаг: [ADR-001 — Представления единого графа знаний](decisions/0001-graph-projections.md).

## 6. Почему данные находятся в отдельном Vault

~~~text
knowledge-skeleton-lab/             ← рабочая папка агента и Git
  AGENTS.md
  rules/                         ← нормативные правила
  prompts/                       ← задания
  experiments/                   ← scope отдельных запусков
  reports/                       ← evidence и ревью
  tools/                         ← валидация
  docs/concept.md                ← объяснение идеи
  vault/                         ← открывать только эту папку в Obsidian
    .obsidian/
    taxonomy/categories/
    knowledge/entries/
    templates/
    views/
~~~

Физическое расположение **не кодирует** предметную область. Знание, относящееся к нескольким категориям, всё равно хранится **в одном файле**. YAML-ссылки внутри заметок считаются от `vault/`, например `"[[taxonomy/categories/async-scheduling]]"`, **без** префикса `vault/`.

При масштабировании физические папки могут быть технически сегментированы, но это не должно менять `id` и смысл классификации.

## 7. Как проверяем полезность

**Статическая валидация (выполняется автоматически):**

~~~bash
node tools/validate.mjs
node --test tools/validate.test.mjs
~~~

Проверяет формат ограниченного YAML subset, UUIDv7, ссылки, типы целей, дубли в свойствах и запрещённые циклы. `PASS` **не доказывает** правильность смысловых отношений.

**Семантическая валидация (независимое ревью):**

| Критерий | Вопрос |
| --- | --- |
| Точность узлов | Каждый узел обозначает самостоятельный референт? |
| Точность рёбер | Отношение действительно соответствует указанному предикату? |
| Дубликаты | Нет ли одного знания под разными именами? |
| Покрытие | Какие темы **независимого baseline** отсутствуют и какие добавлены без оснований? |
| Навигация | Можно ли без ручного просмотра всех файлов найти нужные категории, предков и соседей? |

Для первого пилота достаточно до **30 Knowledge**, минимального набора категорий, проверки всех созданных узлов и ключевых отношений. Следующая итерация проводится **по результатам замечаний**, а не по достижению произвольного размера графа.

## 8. Следующие сценарии после успешного пилота

1. **Расширение одной области:** достроить недостающие узлы, не дублируя существующие.
2. **Добавление смежной области:** повторно использовать категории/знания и показать пересечения.
3. **Обогащение:** написать содержимое нескольких принятых узлов, сохранить все `id` и связи.
4. **Смена классификатора:** проверить, какие вычисляемые группы меняются при перестройке `broader`, не переписывая все заметки.
5. **Воспроизводимость:** передать следующий этап другому агенту только через Git, без контекста чата.

Первый конкретный сценарий: [Asynchronous Programming](../experiments/asynchronous-programming/brief.md); готовое задание: [prompts/first-discovery.md](../prompts/first-discovery.md).

## 9. Границы и нерешённые вопросы

- Построенный граф — **гипотеза о структуре предметной области**; наличие связей не означает доказанную полноту.
- Области и Knowledge должны иметь ясные смысловые границы. Пустые тела заметок повышают риск неявной неоднозначности, поэтому аргументация Discovery хранится в отчёте до обогащения.
- Связи `broader`, `categories` и K–K различаются по смыслу. `part_of` — композиция предметных сущностей, не родительская категория.
- Отношения `uses`, `depends_on`, `prerequisite`, а также типы `instruction` и `implementation` в первом контракте отсутствуют. Их можно предложить после первых проверок, но не добавлять произвольно.
- Obsidian, Bases и графовые плагины — **проекции** данных Markdown/YAML. Отображаемые обратные/выведенные рёбра не становятся новыми предметными фактами.
- Визуализация в GUI требует отдельной ручной проверки; наличие конфигурации в Git не свидетельствует о её успешном запуске.

**Критерий успеха идеи:** граф позволяет восстанавливать структуру области и находить релевантные узлы, а позднее наполнение не требует повторного построения связей и идентичностей — при условии, что семантическое ревью подтвердило их корректность.
