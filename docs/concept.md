# Knowledge Skeleton Lab — актуальная модель

## Назначение

Воспроизводимое исследование предметной области: сначала подтверждаем имена и референты внешними источниками, затем подтверждаем **точные** отношения, после чего строим интерактивные представления.

**Вход:** предметная область, проверяемые внешние публикации, существующие Knowledge.  
**Выход:** направленный Knowledge Graph с трассировкой утверждений к первоисточникам.

## Модель

- **Knowledge** — единственный доменный тип узла, один устойчивый UUIDv7 на референт. Изолированный узел допустим.
- **Typed relation** — утверждение `source → predicate → target` с точной семантикой из [relations.md](../rules/relations.md).
- **Scope** — запрос на просмотр: фокус, типы и направления связей, глубина. Не отдельный вид узла.
- **View** — Obsidian Graph/K-Plex, Bases, Canvas: проекции YAML, не независимый источник предметных фактов.

Внутри Knowledge хранятся `name`, `aliases`, `sources`, статусы и **опциональные** YAML-связи. Физические папки не определяют классификацию. Предметное ревью начинается с идентичности/источников, а не с компоновки графа.

## Текущий пример

Срез Harness Engineering основан на *Agent Harness Engineering: A Survey*, Figure 4: 1 корневое название, 7 направлений, 35 подразделов, 42 авторские связи `in_topic`. Это **проверяемая авторская рубрикация**, не гарантия полноты всей области и не доказательство `part_of`/`specializes`.

## Порядок очистки

1. **Harness contract:** согласовать методы и проверки, не менять существующие узлы.
2. **Node evidence:** проверить каждую карточку по источникам, разрешить дубли и недоказанные имена.
3. **Relation evidence:** проверить каждый предикат/обоснование на подтверждённых узлах.
4. **Presentation:** удалить неактуальные эксперименты и проверить итоговый GUI.

Только одно направление работы за итерацию. Отчёты и старые Canvas не являются нормой, история Git не требует сохранения устаревших копий в рабочем Vault.
