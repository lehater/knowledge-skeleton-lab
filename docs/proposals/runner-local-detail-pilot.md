# Пилот: детализация Runner без новых Knowledge

**Статус:** экспериментальное предложение, не принятое изменение ADR-001.
**Исходная база пилота:** `main`, `e2e0339c6811196c537b74ea43ca1cba455724e8`. Исследование [PR #29](https://github.com/lehater/knowledge-skeleton-lab/pull/29) включено в последующий `main` (`5c8606c`); схема/таблицы ниже учитывают его контрпример.

## Проверяемая польза

Вход — существующий Knowledge OpenAI Agents SDK Runner. Результат — его интерфейс, ограничения, условный сценарий и две локальные таблицы в одной заметке плюс Canvas существующего графового среза. Новых Knowledge, UUID и YAML-рёбер нет.

Проверяем, достаточно ли разделов и встроенных фрагментов для детализации, прежде чем создавать узлы методов, параметров и шагов.

## Предложение для ADR-001

Действующий [ADR-001](../decisions/0001-graph-projections.md) остаётся без изменений. Для последующего решения предлагается добавить:

> Проекция графа показывает канонические YAML-рёбра между Knowledge. Локальная поведенческая диаграмма внутри Knowledge иллюстрирует сценарий, описанный в тексте этой же заметки и подтверждённый её источниками. Её действия, сообщения и переходы не требуют самостоятельных UUID и не становятся рёбрами графа. Диаграмма указывает свой охват и значение стрелок; самостоятельные сущности переиспользуют существующие Knowledge. Новые предметные утверждения сначала описываются в каноническом Knowledge. Canvas продолжает показывать только YAML-рёбра; он может встраивать раздел заметки с локальной диаграммой, не дублируя её действия своими карточками и связями.

Mermaid в этом пилоте проверяет именно эту предлагаемую трактовку. До принятия уточнения его нормативная допустимость остаётся открытым решением; успешные технические проверки не означают принятия предложения.

## Файлы

- `vault/knowledge/entries/openai-agents-sdk-runner.md` — единственное место интерфейса, условий завершения и исходного Mermaid.
- `vault/views/runner-local-detail.canvas` — четыре существующих Knowledge и встроенные разделы Runner. Линии только `realizes` и `in_topic` из YAML, в исходном направлении.
- `experiments/runner-policy/test_runner_policy.py` — два детерминированных SDK-прогона; `ScriptedModel` подменяет только модель, реальный Runner и локальная функция остаются в исполнении.
- `.github/workflows/runner-policy-pilot.yml` — отдельная проверка эксперимента на GitHub Actions с закреплённой версией `openai-agents==0.24.0`.

Карточки одного файла являются повторными представлениями, а не дублями Knowledge. Карточка Mermaid ссылается на раздел через `subpath`; текст схемы в Canvas не копируется. Навигационные body-ссылки не являются YAML-рёбрами, хотя Graph и плагины могут отображать их отдельно: для канонической проекции выбирать только поля отношений.

## Протокол функциональной проверки: две политики SDK

Взять две таблицы из Runner — **«Движение данных»** и **«Условные переходы»**. Для выполнения тестов:

```bash
python -m pip install "openai-agents==0.24.0"
python -m unittest discover -s experiments/runner-policy -p 'test_*.py' -v
```

Нужен Python 3.12 и доступ к PyPI при установке. OpenAI API key не требуется: `ScriptedModel` фиксирует ответы модели, трассировка отключена. Тест проверяет реальный SDK Runner и реальный локальный Python tool, а не работу удалённого LLM.

| Прогон | `tool_use_behavior` | Модель | Вызов инструмента | Ожидаемый `final_output` |
| --- | --- | --- | --- | --- |
| A | `run_llm_again` | 2 вызова; во втором есть `function_call_output` для `call_1` | 1 вызов `get_weather("Tokyo")` | `It is sunny in Tokyo.` |
| B | `stop_on_first_tool` | 1 вызов; второго нет | 1 вызов `get_weather("Tokyo")` | `Tokyo: sunny` |

Тест также вызывает `model.assert_complete()`: если один из подготовленных шагов не потребовался или появилось неожиданное обращение, сценарий не считается успешным.

### Проверка читателем (отдельно от SDK)

1. **До просмотра таблиц** дать читателю четыре Knowledge из [отчёта PR #29](../../reports/harness-engineering/engineering-views-and-graph-semantics.md): Runner, Single-Agent Inner Loop, Tool Call, Tool Result. Задать вопросы ниже и записать ответы с источником: YAML / текст / неизвестно.
2. **После просмотра таблиц** в Runner повторить вопросы и попросить предсказать оба прогона A/B без чтения тестового кода.
3. Сопоставить ответы с фиксированной рубрикой. Считать успешным только точный ответ с условием, а не угаданный путь.

| № | Вопрос | Критерий правильного ответа |
| --- | --- | --- |
| 1 | Что реализует Runner? | Single-Agent Inner Loop; это выражено `realizes` |
| 2 | Кто исполняет локальный инструмент? | SDK Runner инициирует вызов зарегистрированной функции, операция выполняется локальной функцией; не самой моделью |
| 3 | Куда попадает Tool Result? | При A — в следующий запрос модели; при B — непосредственно в `final_output` запуска |
| 4 | Всегда ли будет второй turn? | Нет; только при соответствующей политике и отсутствии иных причин завершения/прерывания |

**Критерий:** 4/4 верных ответов после таблиц и правильный прогноз A/B. Отдельно записать результат до таблиц, чтобы проверить их добавочную ценность. Проверка читателем и GUI выполняется человеком и не может считаться PASS лишь по CI.

### Инварианты эксперимента

Нет новых Knowledge, UUID или YAML-рёбер. Статическая модель остаётся той же при A и B; меняются только значения конфигурации и переходы. Если таблицы достаточны, дальнейшую детализацию остановить. Если не хватает типизированного межузлового поиска, сформулировать конкретный запрос и проверить его на втором механизме до изменения схемы.

## Проверка в Obsidian

1. Открыть Vault из экспериментальной ветки и `views/runner-local-detail.canvas`.
2. Прочитать интерфейс Runner и раздел «Сценарий одного агента» в карточках. Проверить, что Mermaid отрисован, подписи читаемы и цикл понятен.
3. Из карточки открыть Runner; найти методы и `max_turns` без перехода к новым Knowledge. Проверить переходы к Tool Call и Tool Result.
4. Проверить направления трёх линий: Runner → цикл (`realizes`), Tool Call → цикл и Tool Result → цикл (`in_topic`).
5. Временно добавить к строке «Вход» маркер `ПРОВЕРКА`, проверить его появление в Canvas и удалить маркер. Записать фактический результат: автоматическое обновление в Obsidian здесь не проверено.
6. При наличии K-Plex раскрыть заголовки Runner, затем выбрать линзу по полю `realizes`. Проверить, что заголовки доступны без новых файлов, а обычные body-ссылки не выдаются за типизированные отношения. Возможность зависит от установленной версии; результат пока NOT_RUN.

Для проверки Mermaid отдельно от Canvas открыть исходную заметку в Reading view. Это позволяет различить сбой Mermaid и ограничение встраивания раздела в Canvas.

## Сопровождение

Проверка ссылочной структуры должна показать, что изменение раздела не требует правки Canvas. Это проверяет устройство файлов, а не фактическое обновление интерфейса Obsidian.

Текст сценария и Mermaid редактируются вручную вместе. Временное изменение шага в тексте должно выявить, что соответствующую подпись Mermaid нужно исправить отдельно; автоматической синхронизации между ними нет. Условия, не включённые в схему (`max_turns`), явно названы рядом с ней. Условие продолжения после локального инструмента теперь показано на развилке.

При появлении потребности в типизированном поиске по локальной детали отдельно решается вопрос выделения Knowledge. Этот пилот не вводит обязательной иерархии детализации.

## Результаты

- `node tools/validate.mjs` — **PASS**, 236 Knowledge / 228 YAML-рёбер, как в базовом `main`.
- `node --test tools/validate.test.mjs` — **PASS**, 12/12.
- `git diff --check` — **PASS**.
- Разбор JSON Canvas, уникальность идентификаторов, существование файлов и заголовков — **PASS**.
- Все три линии Canvas соответствуют YAML по паре узлов, предикату и направлению — **PASS**.
- Frontmatter Runner, включая UUID и отношения, полностью совпадает с базой — **PASS**.
- Временный маркер в разделе интерфейса прочитан через файловую ссылку карточки; Canvas не менялся, исходная заметка восстановлена — **PASS на уровне файлов**. Обновление карточки в приложении не проверено.
- Временное изменение текста сценария оставило Mermaid неизменным: **подтверждена необходимость ручного сопровождения**. Изменение отброшено.

Проверки пилота выполнены одноразовым скриптом; новая инфраструктура проверки не добавлялась. Mermaid rendering, GUI Obsidian и K-Plex: **NOT_RUN**. SDK-тесты добавлены как отдельный детерминированный прогон; результаты фиксируются по GitHub Actions. Проверяется реальный Runner и локальный инструмент с моделью-заглушкой, а не удалённый LLM.

**Критерий принятия:** оба SDK-теста PASS, читатель правильно предсказывает оба режима и все четыре ответа, в Obsidian переходы работают и изменение раздела отражается во встроенной карточке; затраты на ручное сопровождение Mermaid приемлемы. До этой проверки расширять пример на остальные Knowledge не требуется.
