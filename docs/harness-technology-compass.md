# Технологический компас Knowledge Graph Harness

**Статус:** предложение для обсуждения, не нормативный контракт и не ADR.  
**Область:** построение и развитие семантического графа существующих технологий в Obsidian при помощи Codex и независимого ревью.  
**Сейчас:** создание Knowledge/связей и проверка их качества. Каскадные Canvas отложены.

## 1. Непересекающиеся направления

| Код | Направление | Главная ответственность | Результат / место | Не должно подменять |
| --- | --- | --- | --- | --- |
| **MODEL** | Семантическая модель | Идентичность Knowledge, Category, допустимые предикаты, направление и смысл | `rules/schema.md`, `rules/relations.md`, `rules/taxonomy.md`, ADR при изменении модели | Workflow агента и настройки UI |
| **OPS** | Операции над графом | Повторяемые процедуры создания/расширения/обогащения сущностей | `.agents/skills/` (Discovery сейчас; Enrichment позже) | Утверждение качества собственного результата |
| **GRAPH-QA** | Контроль качества графа | Статическая целостность, независимое семантическое ревью, дубли, релевантность, покрытие | `tools/validate.mjs`, будущий Review Skill, отчёт с вердиктом | Изменение онтологии по инициативе проверяющего |
| **EVAL** | Качество Harness | Проверка **поведения Skills** на повторяемых тестовых заданиях и регрессиях | Будущие `evals/` и тестовые фикстуры | Само ревью реального предметного графа |
| **RUN** | Исполнение и передача | Роли Codex/ChatGPT, ветки, PR, checkpoint SHA, возврат замечаний | `AGENTS.md` как маршрутизатор, GitHub как канал передачи | Предметные решения и новую агентную платформу |
| **DATA** | Хранение и прослеживаемость | Один канонический граф, версии, источники и основания решений | `vault/`, `experiments/<topic>/brief.md`, `reports/`, Git | Дублирование фактов в Canvas или отчёте |
| **VIEW** | Исследование и визуализация | Чтение существующего графа, фильтрация типов связей, навигация | Obsidian / K-Plex; Canvas отложен | Редактирование предметных фактов через картинку |

**Инвариант:** предметная истина о сущностях и отношениях хранится в Knowledge/YAML; Git фиксирует версии. Источники и отчёты служат доказательствами, а не второй копией рёбер. K-Plex — динамический потребитель графа.

## 2. Ответственность на первом end-to-end срезе

```text
Тема и границы исследования                [DATA: brief]
           ↓
Discovery Skill / Codex                     [OPS]
           ↓
Knowledge + YAML-связи, proposed           [MODEL + DATA]
           ↓
Статическая валидация                      [GRAPH-QA: tools]
           ↓
Commit SHA + Draft PR + evidence           [RUN + DATA]
           ↓
Независимый Semantic Review / ChatGPT      [GRAPH-QA]
           ↓
PASS / REVISE / BLOCK с конкретными фактами [GRAPH-QA + RUN]
           ↓
Приёмка решения владельцем, Git            [RUN]
           ↓
Исследование в K-Plex                      [VIEW]
```

- **Discovery создаёт кандидатов**, сохраняет источники и обоснования; не утверждает их семантическую истинность.
- **Review проверяет** точные новые/изменённые узлы и рёбра относительно существующего графа, источников и исходной постановки. Предпочтительно отдельный контекст исполнителя. Вердикт привязан к проверяемому commit SHA; самостоятельное исправление проверяющим — отдельная операция.
- **Валидатор** проверяет формальный контракт; ручной/агентный Review — предметный смысл; **EVAL** проверяет, насколько надёжно сам Harness выполняет процедуру на разных задачах.
- **K-Plex** читает результат. Успешное отображение связей не доказывает предметную корректность.

## 3. Маршрутизация файлов

- `AGENTS.md`: короткая точка входа, глобальные запреты, ссылки на инструкции. Не дублировать полный процесс.
- `rules/`: нормативные значения полей, допустимые отношения и машинно проверяемые инварианты.
- `.agents/skills/<operation>/SKILL.md`: процедура **одного повторяемого действия**, вход, выход, этапы, gate. Не копировать текст `rules/`.
- `tools/`: детерминированная валидация и вспомогательные команды; без скрытых предметных решений.
- `experiments/`: ограниченная постановка тематического среза и независимые контрольные темы.
- `reports/`: evidence, спорные кандидаты, результаты Discovery/Review и ссылки на проверяемые SHA.
- `vault/`: Knowledge и Category; предметные утверждения только здесь.
- `docs/`: концепция, компас и ADR, не источник новых YAML-предикатов.

**Правило изменения:** каждой задаче присваивается основное направление. Если задача затрагивает MODEL, требуется отдельное согласование изменения нормативного контракта. Вторичные изменения допускаются, но должны быть явно названы и проверены.

## 4. Приоритеты и ограничения развития

| Очерёдность | Направление | Минимальное изменение | Gate |
| --- | --- | --- | --- |
| **H0 — уже есть** | MODEL / DATA / GRAPH-QA | YAML v0, правила, идентификаторы, статический валидатор | Базовый формальный граф существует |
| **H1 — сейчас** | OPS + RUN + GRAPH-QA | Discovery Skill (Draft PR), контракт handoff на конкретный SHA, критерии независимого Review | Один завершённый цикл Discovery → Review без правки `main` |
| **H2** | EVAL | 3–5 тестов: новая тема, повтор, смежная тема, двусмысленная связь, запрещённый предикат | Оцениваемые результаты и воспроизводимость |
| **H3** | GRAPH-QA + OPS | Review Skill, независимый запуск и обратная передача замечаний | Измеримая выявляемость дублей/семантических ошибок |
| **Позже** | OPS / VIEW / RUN | Enrichment, обслуживание графа, улучшения K-Plex, автоматизация handoff | Только по выявленным ограничениям |

### Пока не делать

- Не создавать оркестратор, новую базу графа, фреймворк поверх Codex или дополнительные роли без потребности.
- Не смешивать генерацию графа с Semantic Review в одном самоподтверждающем этапе.
- Не добавлять новых отношений только ради визуальной связности.
- Не делать Canvas источником истины и не строить каскадные Canvas на текущей итерации.
- Не считать Static PASS, GUI PASS или отчёт генератора доказательством независимой предметной приёмки.

## 5. Минимальная следующая задача

Согласовать контракт Discovery → Review (точный `base SHA`, `candidate SHA`, diff, brief, список узлов/рёбер, источники, статические проверки и формат замечаний), затем выполнить один небольшой E2E на экспериментальной ветке. После фактического запуска корректировать Skill по evidence.
