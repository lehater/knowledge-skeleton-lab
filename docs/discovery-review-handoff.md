# Discovery → Semantic Review: контракт передачи v0

**Статус:** proposal, не нормативное правило и не утверждённая процедура.  
**Направление технологического компаса:** RUN (передача и версии) + GRAPH-QA (ревью).  
**Применение:** инкрементальное создание Knowledge/Category и типизированных YAML-связей; Canvas и каскадная навигация вне рамок.

## 1. Цель и границы

Обеспечить воспроизводимый цикл между **локальным Codex (Discovery)** и **отдельной сессией ChatGPT (Semantic Review)** через GitHub. Исполнители могут меняться: контракт определяется артефактами, а не чатом или конкретной моделью.

- Единственный канонический предметный граф — `vault/knowledge/entries/` и `vault/taxonomy/categories/`, согласно `rules/`.
- Источники, обоснования, PR и вердикты — проверяемое **evidence**, не второй набор предметных YAML-отношений.
- **Static validation** доказывает формальную целостность; **semantic review** оценивает предметную достоверность; **harness evals** тестируют повторяемость и качество самого рабочего процесса. Эти уровни не взаимозаменяемы.
- Новые Knowledge остаются `review_status: proposed`. `PASS` конкретного Review не меняет статусы автоматически и не означает принятие владельцем.

## 2. Вход/выход и ответственности

| Этап | Исполнитель | Вход | Выход | Ответственность |
| --- | --- | --- | --- | --- |
| Scope | Владелец + Discovery | Тема и ограничения | `experiments/<topic>/brief.md` | Границы `in/out`, лимит, контрольные темы и ожидаемая польза |
| Discovery | Локальный Codex | `brief`, полный текущий граф, `rules/`, источники | Candidate Knowledge/Category + ссылки, `reports/<topic>-discovery.md` | Переиспользование, выбор предметных референтов, обоснование каждого прямого ребра |
| Static gate | Локальный Codex / инструменты | Candidate working tree | Результаты `validate`, тестов и diff | Формальная корректность и допустимый набор изменённых файлов |
| Handoff | Локальный Codex | Чистый checkpoint-кандидат | Draft PR + `base_sha` + `candidate_sha` | Доступность полного воспроизводимого пакета в GitHub |
| Semantic Review | ChatGPT, отдельный контекст | Именно указанные SHA, `brief`, diff, предметный граф, evidence | PR Review/comment с вердиктом и замечаниями | Независимая проверка всех изменённых узлов/рёбер, дубликатов, источников, границ, классификации |
| Decision | Владелец | Review verdict | Решение принять, исправить или остановить | Управление приёмкой; не делегируется генератору |

## 3. Неизменяемые якоря

- **`base_sha`** — точный commit исходного дерева до рассматриваемой итерации.
- **`candidate_sha`** — точный commit с кандидатным графом и отчётом Discovery.
- **`diff`** — изменения `base_sha..candidate_sha`, включая все затронутые существующие файлы; сравнение не ограничивается списком новых карточек.
- Оба SHA обязательны и указываются полными 40-символьными значениями. Ветку и номер PR можно использовать для навигации, **но не вместо SHA**.
- Если `candidate_sha` не восходит к `base_sha`, либо diff захватывает чужие изменения, подготовить отдельный чистый checkpoint или явно остановить ревью до определения границ.
- Изменение кандидата создаёт новый `candidate_sha`; прошлое заключение сохраняется как историческое свидетельство и не переносится автоматически на новый HEAD.

## 4. Пакет Discovery (минимальный)

Передаваемый PR должен содержать:

1. `brief.md`: тема, узкий срез, что исключено, лимит, независимые контрольные темы/источники.
2. Git diff: новые/изменённые Knowledge, Category и направленные YAML-связи; без новых предикатов и расширения схемы.
3. Отчёт Discovery: какие существующие Knowledge **переиспользованы**, какие созданы, какие изменены; для **каждой новой/изменённой предметной связи** — source, predicate, target, обоснование и источник; спорные кандидаты; непокрытые темы и ограничения.
4. Gate evidence: команды, результаты, число новых/изменённых Knowledge, Category и рёбер, список файлов; статусы `NOT_RUN` для невыполненных проверок.
5. Точную ссылку на Draft PR и оба SHA в сообщении передачи.

Не нужно переносить полные YAML-файлы в отчёт: они уже находятся в Git. Таблица отношений в отчёте нужна как **обоснование и индекс проверок**, не как каноническая копия графа.

### Формат сообщения передачи

```text
Discovery handoff
PR: <ссылка>
base_sha: <40-символьный SHA>
candidate_sha: <40-символьный SHA>
brief: experiments/<topic>/brief.md
report: reports/<topic>-discovery.md
static: PASS | FAIL | NOT_RUN
independent semantic review: NOT_RUN
GUI / K-Plex: NOT_RUN (если GUI не проверялся)
```

Если обязательного артефакта нет, reviewer отмечает его отсутствие; отсутствие данных не превращается в PASS.

## 5. Процедура независимого Review

1. Получить `brief`, `AGENTS.md`, применимые `rules/` и оба Git SHA **напрямую из GitHub**; не использовать историю чата как источник фактов о графе.
2. Сверить `diff` и пакет передачи: нет незаявленных изменений существующих знаний, категорий, статусов, IDs, нормативных правил или UI.
3. **Проверить каждую новую/изменённую сущность** относительно всего доступного графа (`name`, `aliases`, смысловой референт), выявить дубли, неоднозначные понятия, различие общего знания и реализации.
4. **Проверить каждую новую/изменённую связь**: правильность направления, точного предиката, типа участников и предметного основания. `categories` и `broader` проверять отдельно от K–K отношений.
5. Проверить границы выборки и релевантность Knowledge исходному `brief`; покрытие оценивать **только** относительно независимого baseline, а не числа созданных карточек.
6. Сверить существенные утверждения с первичными источниками; записать проверенное покрытие, отсутствующие доказательства и факты, которые не удалось подтвердить. Самоутверждения Discovery не считать независимой проверкой.
7. Зафиксировать вердикт **в PR comment/review с явным `candidate_sha`**. Reviewer по умолчанию не редактирует предметные YAML и не меняет `review_status`.

Не требуется заново изучать весь граф в деталях, но проверка **дублей** должна охватывать весь корпус, а проверка **затронутых рёбер** — все их прямые новые и изменённые экземпляры. Для малой партии это реализуемый полный контроль изменений.

### Замечание Reviewer

Каждое замечание записать как: `P0 | P1 | P2 | P3`; референт (путь/узел/тройка `source → predicate → target`); фактическая проблема; источник/обоснование; конкретное необходимое действие.

- `P0`: нарушение целостности, необоснованное разрушение или дублирование канонической идентичности, запрещённая правка контракта.
- `P1`: существенная недоказанная или неверная семантика, неверный предикат, дублирование по смыслу, нерелевантный Knowledge.
- `P2`: улучшение классификации, гранулярности или доказательной базы без критического нарушения.
- `P3`: оформление и читаемость evidence.

### Вердикт

| Вердикт | Значение | Дальнейшее действие |
| --- | --- | --- |
| `PASS` | Все изменённые сущности/связи рассмотрены, существенных P0/P1 нет, evidence достаточен в пределах заявленного scope | Владелец решает о приёмке |
| `REVISE` | Обнаружены исправимые P0/P1 либо неполное существенное обоснование | Codex исправляет в той же экспериментальной PR-ветке, повторное Review нового SHA |
| `BLOCK` | Некорректные границы, неотделимые чужие изменения, недоступные обязательные исходные данные, неразрешимое противоречие контракту | Остановить цикл до решения владельца |
| `NOT_RUN` | Независимая семантическая проверка не проводилась | Не заявлять предметную приёмку |

`PARTIAL` — **объём свидетельств**, а не эквивалент `PASS`: явно указать, что и почему не проверено, и использовать `REVISE` или `BLOCK` при существенном пробеле.

### Формат результата в PR

```text
Semantic Review
candidate_sha: <полный SHA>
base_sha: <полный SHA>
verdict: PASS | REVISE | BLOCK
scope: <brief / изменённые файлы>
coverage: <сколько новых/изменённых узлов и рёбер просмотрено; какие источники проверены>
static gate: independently reproduced PASS | reported PASS, not reproduced | FAIL | NOT_RUN
findings:
- P1: <предметный референт / связь> — <проблема>; evidence <ссылка>; action <исправление>
limitations: <непроверенное / отсутствующее>
GUI / K-Plex: NOT_RUN (если проверка не проводилась)
```

## 6. Цикл исправлений

1. ChatGPT публикует Review на `candidate_sha`.
2. Codex читает конкретный Review из GitHub, исправляет только обоснованные замечания и создаёт новый commit; сохраняет старый отчёт как evidence или обновляет итоговый с указанием предыдущей версии.
3. Для следующего Review **`base_sha` остаётся прежним**, `candidate_sha` меняется на новый SHA, а проверяющий сверяет весь накопленный diff и исправления замечаний.
4. Новые обнаруженные ошибки могут изменить вердикт. PASS одного коммита не распространяется на последующие.
5. Принятие и объединение ветки — отдельное действие владельца; `main` не изменяется автоматически.

## 7. Первый E2E gate

Запустить один срез до 5–8 новых Knowledge. Проверить: полнота handoff-пакета, отсутствие семантических дублей, валидность всех прямых рёбер, воспроизводимость статической проверки, наличие независимого Review на зафиксированный SHA и корректный возврат замечаний в Codex.

**Не входят в v0:** автоматическая оркестрация ChatGPT ↔ Codex, API для вердиктов, второй реестр графовых фактов, автоматическое изменение `review_status`, Canvas и отдельный Review Skill. Review Skill позднее должен исполнять этот же контракт, а не создавать другой.
