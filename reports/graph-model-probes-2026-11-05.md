# Проверка выразительности Knowledge Graph на сложных связях

**Дата:** 2026-11-05. **База:** GitHub `main` `4814addbc6313e427faa9d3ab768f2f79d197667` (миграция `kind`, PR #37). **Статус:** исследовательский эксперимент; решение о схеме не принято. **Контрольный код:** [model-probes.test.mjs](../../experiments/graph-model-probes/model-probes.test.mjs).

## 1. Проверяемая гипотеза и граница полноты

Гипотеза: восемь текущих YAML-предикатов достаточно точно описывают **устойчивые предметные связи** для учебного Knowledge Graph; структурные/функциональные запросы и сценарии с изменяемыми участниками должны отделяться от тематической навигации.

Нельзя доказать «полноту для всех сущностей программной инженерии» перебором текущих Knowledge. Проверяем **пригодность для набора конкретных вопросов**:
1. Достаточность: существует ли в YAML честная связь, из которой выводится ответ на заданный инженерный вопрос?
2. Точность: не смешиваются ли `in_topic`, `specializes`, `part_of`, `realizes`, `schedules`, `executes`, `manages`?
3. Независимость от конфигурации: сохраняется ли устойчивый факт, когда меняются маршруты, количество экземпляров и режимы?
4. Граница знания: где ответ дан текстом/контрактом, а не ребром, и действительно ли нужен повторяемый **межузловой запрос**?

Различаем **природу референта** (`kind`), **типовую связь** (YAML), **конфигурацию/сценарий**, **конкретный запуск/трассу**. Синтаксический PASS и низкая доля функциональных рёбер сами по себе не доказывают ни семантическую правильность, ни неполноту.

### C4–C5: различие между типом части и экземпляром в конфигурации

Источник: [OpenTelemetry Collector Architecture](https://opentelemetry.io/docs/collector/architecture/) и [Configuration](https://opentelemetry.io/docs/collector/configuration/). Pipeline требует минимум один совместимый Receiver и Exporter; Processors необязательны. Один Receiver может обслуживать несколько Pipeline; для общего имени Processor в разных Pipeline создаются отдельные экземпляры. Поэтому нельзя из одного `Receiver → part_of → Pipeline` вывести количество receiver instances или адрес конкретной передачи.

Контрольные сценарии (синтетические, **не** новые Knowledge):
- A: `Receiver → Processor → Exporter`;
- B: `Receiver → Exporter`.

Статическая типовая структура одинаковая, фактическая последовательность другая. Это контрпример **восстановлению маршрута из типового графа**, а не опровержение самого `part_of`. Ответ должен жить в конфигурации/локальном сценарии, пока у проекта нет требования строить единый машиночитаемый маршрут.

### C6: множественные участники и вхождения

Для Tool Call / Tool Result конкретный ответ связан с конкретным вызовом через контекст протокола и ID. Два исполнения могут содержать те же **типы** Knowledge, но разные пары конкретных `call_id/result_id`. Плоское бинарное ребро между типами не заменяет запись об одном взаимодействии. По [W3C N-ary Relations](https://www.w3.org/TR/swbp-n-aryRelations/) отношения, требующие нескольких участников, свойств или порядка, часто моделируют отдельным экземпляром отношения; в текущем проекте такой уровень следует оставить **локальному сценарию**, если он не нужен для межузлового поиска.

### C7: главное новое направление проверки

Два независимых примера показывают смежную проблему: **API-объект/handle** и **исполняемая деятельность** — разные референты. `specializes` утверждал бы разновидность деятельности, `realizes` — реализацию названной абстракции, `part_of` — композицию; здесь ни одна замена не очевидна. `in_topic` честно сохраняет контекст, но не позволяет ответить на запрос «какие API-конструкции представляют исполняемые работы?».

Кандидатная семантика для следующего **смыслового**, а не технического эксперимента: `represents_execution` / «представляет управляемое исполнение» с конкретными вопросами и отрицательными примерами (например, Future с результатом без собственного исполнения). **Новый предикат не утверждён**: сначала проверить, соответствует ли он первоисточникам и будет ли полезен в Obsidian хотя бы в двух независимых технологических областях.

## 4. Проверка и связь с ранними исследованиями

Воспроизводимая команда:

```bash
node --test experiments/graph-model-probes/model-probes.test.mjs
```

Тесты **не** запускают OpenTelemetry Collector и SDK, **не** открывают Obsidian и **не** доказывают семантическую правильность 638 рёбер. Они проверяют текущую структуру, воспроизводят ограничения двух разных миров с одинаковой типовой проекцией и демонстрируют границу статического валидатора.

Исследования [PR #29](https://github.com/lehater/knowledge-skeleton-lab/pull/29) и [закрытого PR #32](https://github.com/lehater/knowledge-skeleton-lab/pull/32) уже показали отсутствие маршрутов, обязательности ролей и потенциальную семантику `requires_role` / `responds_to`. Настоящий эксперимент **добавляет корпусную проверку после миграции `kind` и пару C7**, не повторяет поиск новых предикатов с нуля. PR #32 уже проверял вторую потенциальную необходимую роль (`asyncio.Task` требует совместимый running Event Loop для продвижения вычисления), но польза машинного запроса пока не показана.

## 5. Решение и приоритеты

- **P0:** не объявлять модель «полной» для любой функциональной архитектуры. Для **статической карты понятий, частей, реализаций и исполнительских ответственностей** существенные положительные случаи проходят. Для **маршрутов, кратности, обязательных ролей, контекстных условий и вхождений** только YAML недостаточно. Это согласуется с ADR-001.
- **P1:** уточнить семантическую границу отношений **типов** и **экземпляров** у `part_of`, `manages`, `schedules`: иначе статическая роль может быть прочитана как факт конкретного исполнения.
- **P1:** проверить C7 на новом независимом объекте, затем решить, оправдан ли отдельный запрос о связи API-конструкции с исполняемой работой. **Нельзя автоматически переименовывать `in_topic` в `realizes`.**
- **P1:** взять 10–15 реальных рёбер `in_topic` с целевым `kind ≠ topic`, отобранных **по неоднозначности**, а не по случайной частоте, и пройти `source → утверждение → допустимый предикат → требуемый запрос`. Не создавать сплошной evidence-реестр.
- **P2:** отдельно проверить функциональную читаемость одного механизма в Obsidian: кто исполняет, что требуется на входе, что получается на выходе и какой маршрут зависит от конфигурации. Сопоставить результаты фильтра YAML и текста Knowledge; GUI-проверка сейчас **NOT_RUN**.
- **P2:** считать `requires_role` и `responds_to` прежними гипотезами (PR #32), а не завершённой миграцией. Новый предикат оправдан лишь после доказанного повторяемого запроса, не решаемого локальным описанием/сценарием.

## 6. Критерий следующего решения

Не увеличивать словарь автоматически. Зафиксировать **три пользовательских вопроса**, которых сейчас не хватает при изучении системы, и проверить на **двух независимых механизмах**:

1. Ответ уже выводится из восьми рёбер → **модель достаточна для этого запроса**.
2. Ответ существует в Knowledge или привязан к сценарию/конфигурации → **нужно подходящее представление, не обязательно новый предикат**.
3. Существует устойчивый предметный факт между Knowledge, его нужен находить фильтром и стандартные отношения искажают смысл → **обоснование узкого нового предиката**.

**Вердикт эксперимента:** текущая модель пригодна для узкой канонической типовой сети и честно показывает ряд инженерных связей; её «полнота» в смысле всей функциональной архитектуры не подтверждена. Приоритет следующей итерации — проверить повторяемую семантическую потерю в конкретных `in_topic`, прежде чем что-либо менять в `main`.

### 7.1. Отбор, референты и статусы

Взяты **ровно 15 существующих в main рёбер**. Отбор целевой по риску: construct/process (2), свойство/практика/обзор (2), программный интерфейс (1), поле протокольного контракта (1), компонент/обязательная роль/маршрут Collector (4), механизм/исполнение/управление (3), реализация цикла (1), ответ инструмента (1). Для каждого фактические пары и kind проверены непосредственно в карточках. Все пары дополнительно утверждаются тестом F1. Синтетические объекты **не добавлялись** в Vault.

Единица оценки: «source (kind) — фактический predicate — target (kind) — конкретный инженерный запрос». Рёбра могут быть семантически верны, но недостаточны **для другого, более узкого запроса**. Это query-gap, а не автоматически ложная связь.

- SUPPORTED: ответ на указанный вопрос выводится из существующих рёбер.
- CONTENT_ONLY: факт находится в содержимом карточки/контракте; необходимость отдельного межузлового запроса пока не доказана.
- VIEW_DEPENDENT: ответ зависит от конфигурации, экземпляра или сценария.
- GAP: указанный вопрос в текущей типовой проекции YAML неразрешим; новый предикат **не следует** из одного этого статуса.
- INCORRECT: зафиксировано конкретное утверждение, противоречащее первоисточнику; отмечаем, в каком носителе ошибка.

### 7.4. Реальная ошибка E1 и три класса пробелов

**E1, P1 — фактически неверное безусловное утверждение в содержимом.** Карточка [Tool Result](../../vault/knowledge/entries/tool-result.md) начинается с утверждения, что результат вызова «возвращаемый в контекст следующего обращения модели». Это некорректно как инвариант: [Agents SDK](https://openai.github.io/openai-agents-python/agents/#tool-use-behavior) документирует run_llm_again и stop_on_first_tool; во втором случае ответ инструмента используется как итог **без следующего LLM-вызова**. При будущей отдельной правке предлагается текст:

> Tool Result — результат исполнения вызова инструмента. По контракту протокола и политике выполнения приложение может передать его модели для следующего шага либо использовать для завершения исполнения. Сам факт получения результата не гарантирует новый вызов модели.

Нормативная модель и фактическое YAML-ребро здесь не ошибочны; текст исправляется **существующей моделью**. Изменять Vault в этом исследовании нельзя, поэтому правка предложена, но не внесена.

**G1 — конструкция ↔ исполняемая работа (S01/S02).** Два реальных языка, но нет гарантии одной точной семантики: Java Thread прежде всего представляет управляемый поток; asyncio.Task выполняет coroutine и хранит результат. Имеющиеся realizes и executes уже дают два независимых выразительных способа (S12/S14). Проверка «подойдёт ли realizes после уточнения референта» предшествует изобретению represents_execution. Отрицательный пример: asyncio.Future имеет результат без собственного выполнения coroutine. Инстанс Java Thread до start не подтверждает факт *идущего* исполнения.

**G2 — обязательность роли в работающем механизме (S07/S09).** Collector даёт две необходимые роли **одного** механизма. Processor опционален. InputSchema обязательно в MCP Tool Definition, но это **поле спецификации**, не функциональная роль. PR #32 независимо проверял Inspect AI Task и Temporal Replay: обобщение там дало бы иной смысл. Второй независимый положительный **механизм** для requires_role не получен. В текущей итерации достаточно описания Pipeline; инстансную кратность и путь оставить конфигурации.

**G3 — соответствие типа ответа и запроса (S15, вторичный пробел).** Tool Result и Tool Call относятся к одному контракту; MCP и OpenAI/Claude SDK дают протокольные примеры. Однако в графе это те же две обобщённые карточки, не две независимые предметные пары. Типовое responds_to, даже появившись, не восстановит фактические request/result IDs и условный путь следующего turn. Польза повторяемого межузлового поиска по нескольким *разным* парам не доказана.

**Подтверждённые вопросы, которые YAML не решает:** «Найти все API-конструкции, представляющие работу», «Найти обязательные функциональные роли», «Найти тип ответа по типу запроса». Это **три query-gap класса, пять наблюдений в 15 случаях** (S01/S02/S07/S09 и вторичный S15). Считать их пятью ошибками графа или требованием добавить три предиката нельзя.

### 7.5. Решение по шести критериям нового предиката

| Критерий | G1 construct/execution | G2 required role | G3 response type |
|---|---|---|---|
| 1. Однозначная независимая семантика | **Не доказана**; represents/realizes/executes пересекаются по разным референтам | Определима в строго заданном scope | Определима для типов протокольных сообщений |
| 2. Авторитетный первоисточник | Да, Oracle + Python | Да, OpenTelemetry | Да, MCP + SDK |

### 7.6. Классы инженерных вопросов и приоритеты

**Уже поддерживаются:** тематический поиск, is-a при определённом референте, типовой состав, реализация абстрактного цикла, ответственные за исполнение Pipeline, планирование Task, выполнение Coroutine и управление жизненным циклом Tasks. Ответ выводится из YAML без интерпретации локальной конфигурации.

**Не поддерживаются как масштабируемый межузловой YAML-фильтр:** три вопроса G1–G3. Это ограничение текущих запросов, а не доказательство универсальной недостаточности метамодели.

**P0:** критических новых ошибок модели не обнаружено. Сохранить запрет на перенос типовых рёбер в инстансы и не вводить flows_to или depends_on по соседству компонентов.

**P1:** исправить E1 отдельным содержательным PR, не меняя kind и предикаты. Перед обсуждением G1 проверить реальный запрос и возможность использовать существующие realizes/executes с точными референтами.

**P2:** обязательность ролей и типы ответов пока оставить в карточках/представлениях; вернуться к предикатам только после двух независимых механизмов и пользовательского запросного теста. Для маршрутов использовать конфигурацию, не канонический типовой граф.

**P3:** GUI-испытание K-Plex/Bases делать при подтверждённой потребности в конкретном фильтре; GUI-тест не подтверждает онтологическую истинность ребра.

**Общий вывод.** Для исследованных типовых отношений модель **достаточна**. В одном тексте найдено безусловное неверное утверждение; ни одного доказанно ложного YAML-ребра из 15. Запросные потери реальны, но необходимый для нормативной миграции набор из шести критериев не выполнен ни для одного кандидата. **Метамодель пока не расширять.** Полнота графа для всех инженерных задач не доказана.

## 8. Решение по G1 — повторяемый запрос к программным конструкциям (2026-11-07)

**Статус:** независимая документальная и машинная проверка *выразимости*, без изменения действующих YAML-связей. Проверенная база — main 4814addbc6313e427faa9d3ab768f2f79d197667.

### 8.1. Три разных инженерных вопроса

1. **Q1. Реализация абстракции:** «Какие программные конструкции конкретно воплощают Thread или Asynchronous Task?» Кандидат существующего предиката — **realizes**, направление от реализации к абстракции.
2. **Q2. Исполнение:** «Какая конструкция исполняет Coroutine Object?» Уже отвечает **executes**: Python asyncio.Task → Python Coroutine Object.
3. **Q3. Тематическое соседство:** «Какие технологии обсуждаются в теме Thread?» Уже отвечает **in_topic**.

Эти запросы имеют разные требования к точности; слово «представляет» нельзя без разборки использовать как общий предикат.

### 8.2. Первоисточники и границы референтов

| Пара/контрпример | Содержание первоисточника | Решение |
|---|---|---|
| Java Thread (program_construct) → Thread (process) | [Oracle Java SE 27 Thread](https://docs.oracle.com/en/java/javase/27/docs/api/java.base/java/lang/Thread.html): класс предоставляет создание, запуск, ожидание и управление потоком; объект может существовать до запуска. | Возможная **типовая реализация** абстракции Thread через realizes; наличие объекта не означает, что конкретный поток уже исполняется. Не подменять specializes или executes. |
| Python asyncio.Task (program_construct) → Asynchronous Task (process) | [Python 3.15 asyncio.Task](https://docs.python.org/3.15/library/asyncio-task.html#task-object): Task обеспечивает исполнение coroutine, хранит состояние и позволяет ожидать итог. | Возможная реализация управляемой async-работы через realizes; независимое фактическое executes → Coroutine Object уже есть. |
| Python asyncio.Future (program_construct) | [Python 3.15 Futures](https://docs.python.org/3.15/library/asyncio-future.html): Future представляет ожидаемый результат, не гарантирует самостоятельное исполнение. | Отрицательная граница: не объявлять Future реализацией исполняемой Asynchronous Task лишь из-за kind или внешнего сходства. |
| Python threading (software) → in_topic → Thread | [Python 3.15 threading](https://docs.python.org/3.15/library/threading.html): модуль предоставляет инструменты для создания и управления потоками; сам модуль не поток исполнения. | Подтверждённый негативный пример ложного ответа Q1 при поиске только через in_topic. |
| OpenAI Agents SDK Runner → realizes → Single-Agent Inner Loop | [SDK Running agents](https://openai.github.io/openai-agents-python/running_agents/): Runner осуществляет агентный цикл. Ребро уже есть в main. | Существующий прецедент realizes от program_construct к process; универсальная необходимость нового предиката для такой пары опровергнута. |

**Ограничение:** кандидатные Java Thread → realizes → Thread и asyncio.Task → realizes → Asynchronous Task рассматриваются как *типовые семантические гипотезы*, а не новые подтверждённые YAML-факты. Решение об их добавлении требует предметной проверки каждого референта: процесс описывает абстракцию работы, реализация обеспечивает соответствующий контракт, а не лишь ассоциирована с темой.

### 8.3. Воспроизводимый запросный тест

К существующему эксперименту добавлены три теста **F10–F12** (теперь 19 исследовательских тестов):

- **F10:** входящие связи in_topic к Thread находят Java Thread и Python threading. По одному тематическому ребру Q1 решить нельзя: API-конструкция и модуль имеют разные предметные обязанности.
- **F11:** в *синтетической проекции в памяти* добавляются две гипотетические реализации, но реальные карточки остаются без изменений. Обратный запрос realizes к Thread и Asynchronous Task находит ожидаемые конструкции. **Доказано, что класс запроса можно выразить существующим словарём при принятой предметной аннотации**, не доказано, что эти два ребра уже приняты.
- **F12:** asyncio.Future (также program_construct) не объявляется реализацией Asynchronous Task. Существующее executes от asyncio.Task к Coroutine Object не подменяет реализацию абстракции. Нельзя генерировать связи по комбинации kind.

Контрольный инженерный запрос Q1 после *гипотетического* разрешения двух пар может выполняться обычным входящим фильтром **realizes**. Специальный represents_execution не даёт доказанного нового запроса по сравнению с ним.

### 8.4. Решение

| Проверяемый тезис | Результат |
|---|---|
| «Для Q1 недостаёт типа предиката» | **Нет:** realizes достаточно по *выразимости*. |
| «Q1 уже работает в каноническом графе» | **Нет:** две пары сейчас записаны как in_topic. Это неразмеченная конкретная семантика, не дефект словаря. |
| «Нужно автоматически заменить эти два ребра» | **Нет:** каждый факт требует самостоятельного Source-First подтверждения; текущий PR исследовательский, Vault менять запрещено. |
| «G2 / G3 решены» | **Нет:** обязательные роли и соответствие запрос/ответ остаются без машинного межузлового индекса; критерии нового предиката ещё не выполнены. |
| «Нужно добавлять новый предикат для G1» | **Нет:** различимая независимая семантика и новый запрос сверх realizes не доказаны. |

**Приоритеты:** **P1** — при подтверждённой потребности в Q1 провести отдельную семантическую правку двух связей, проверяя реальные абстракции и отрицательный Future. **P2** — не мигрировать остальные in_topic механически. **P3** — GUI-проверку проводить только при конкретной потребности в таком фильтре.

**Итоговое архитектурное решение по текущей выборке:** оставить **восемь** предикатов. G1 закрыт на уровне *выразимости*, но две фактические пары ещё не размечены типом realizes. G2/G3 остаются документированными ограничениями конкретных запросов без доказательства необходимости расширения. Ошибка E1 исправлена **в отдельном Draft PR #40** (проверки PASS), но в main ещё не объединена. Ни один из двух PR самостоятельно не сливать.

**Границы:** исходный Vault, UUID, kind, relations, правила, схема и main не изменены; тесты F10–F12 — только статический корпус и гипотетическая проекция, а не испытание Java/Python runtime. Утверждения о полноте графа не делаются.
