## Вывод

**Вывод PR #31 «в одном информационном маршруте новые предикаты не нужны» правилен в его границах, но не является доказательством достаточности всего словаря.** На существующих Knowledge обнаружены как минимум **два осмысленных, пока невыразимых статическими рёбрами вопроса**: (1) какие роли обязательны для работы Pipeline? (2) каким сообщением по протокольному контракту отвечает Tool Call? Прямые рёбра потока конкретных экземпляров по-прежнему некорректны без указания конфигурации. Добавлять новые предикаты прямо сейчас не рекомендуется: сначала подтвердить ценность запросов на нескольких механизмах.

## 1. Процедура проверки предиката

Для кандидата задаём вопрос пользователя, затем проверяем пять критериев:

1. **Существующие референты:** оба конца — отдельные существующие Knowledge, а не скрытые параметры текущего запуска.
2. **Необходимый смысл:** первоисточник подтверждает отношение; указаны направление, роли, уровень утверждения (тип/экземпляр) и условия.
3. **Контрпример:** утверждение не превращается в ложь при другой допустимой конфигурации в заявленных границах.
4. **Новый запрос:** ни `in_topic`, ни `part_of`, ни один из остальных 6 предикатов не отвечают на тот же вопрос без подмены семантики.
5. **Стоимость:** отношение полезно для повторяющихся межузловых вопросов, а не только как иллюстрация в одной карточке. При многоместности/параметрах сначала использовать локальную таблицу или сценарий.

**«Устойчивое» не означает «всегда исполняется».** Надо различать требуемую роль, поддерживаемую возможность, потенциальный обмен, путь выбранной конфигурации и фактическое событие. Это разные утверждения. Аналогичные классы в [ArchiMate 101](https://archimate-community.pages.opengroup.org/workgroups/archimate-101/): Serving, Access, Flow, Triggering; из этого не следует их автоматическое включение в нашу схему. [W3C N-ary Relations](https://www.w3.org/TR/swbp-n-aryRelations/) отдельно объясняет недостаточность бинарного ребра при существенных дополнительных аргументах.

## 2. Collector: обнаружено различие `part_of` и «обязателен для»

В `main` имеются четыре структурных ребра вокруг Pipeline: `Pipeline → part_of → Collector`; `Receiver/Processor/Exporter → part_of → Pipeline`. Ровно это даёт состав *в терминах архитектурных ролей*, но не обязательность участия.

[Официальная архитектура OpenTelemetry Collector](https://opentelemetry.io/docs/collector/architecture/) фиксирует:
- receiver собирает данные; processor — **необязательная** стадия;
- exporter отправляет данные; допустим Pipeline без processors;
- один receiver может обслуживать несколько pipelines; порядок/путь задаётся конфигурацией.

В [пакете receiver](https://go.opentelemetry.io/collector/receiver) прямо указано: в допустимой конфигурации Pipeline должен быть хотя бы один включённый receiver. В [проверке конфигурации Collector](https://github.com/open-telemetry/opentelemetry-collector/blob/main/otelcol/config.go) также требуется exporter для обычной конфигурации (с учётом feature-gate `AllowNoPipelines`); connectors могут выполнять роли соответствующих сторон. Утверждение здесь **о логических ролях работоспособного конвейера, не о конкретных экземплярах, дистрибутиве и каждой специальной сборке**.

| Проверка | `main` | Кандидат для модели ролей | Значение |
| --- | --- | --- | --- |
| Из чего типологически состоит Pipeline? | `Receiver/Processor/Exporter → part_of → Pipeline` | Не нужен | Вопрос уже решён |
| Какие роли обязательны в активном Pipeline? | **Не выводится:** `part_of` одинаков для обязательных и необязательных ролей | `Pipeline → requires_role → Receiver` и `Pipeline → requires_role → Exporter` | Новое полезное различие |
| Кому receiver отдаёт конкретные traces? | Не выводится | **Не** `Receiver → sends_to → Processor` | Получатель меняется при исключении processor |
| Передаёт ли processor каждый пакет exporter? | Не выводится | Не безусловное ребро | Фильтрация может отбросить пакет |

`requires_role` — **исследовательская иллюстрация**, а не утверждённое имя предиката. Семантика: «для рассматриваемого класса работоспособных систем требуется ≥1 участник, реализующий роль-цель». Количество и совместимость остаются в тексте Pipeline. В отличие от общего `depends_on` это не означает кодовую, сетевую или временную зависимость. В отдельных случаях роль может реализовать Connector — он не превращается в экземпляр Knowledge Receiver.

**Выигрыш будущей фильтрации:** структурный вид покажет все три роли; вид обязательных зависимостей — только Receiver и Exporter. Эту разницу невозможно восстановить фильтрацией только существующих типов.

## 3. Runner: независимая проверка и отрицательные примеры

Существующие Knowledge: [Runner](../../vault/knowledge/entries/openai-agents-sdk-runner.md), [Inner Loop](../../vault/knowledge/entries/single-agent-inner-loop.md), [Tool Call](../../vault/knowledge/entries/tool-call.md), [Tool Result](../../vault/knowledge/entries/tool-result.md).

- `Runner → realizes → Single-Agent Inner Loop` уже корректно выражает конкретизацию абстрактного цикла.
- **Нельзя** `Runner → depends_on → Tool Call` в смысле обязательности: [Runner](https://openai.github.io/openai-agents-python/running_agents/) может завершиться без вызова инструмента.
- **Нельзя** `Runner → produces → Tool Result` без уточнения, кто исполняет инструмент и какой результат считается полученным.
- `Tool Result → responds_to → Tool Call` — **кандидат на стабильную связь между концептами протокольных сообщений**. В [MCP Tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools) `tools/call` получает ответ `CallToolResult` (в том числе с `isError`). Такой ответ связан с вызовом, но **не каждый запрос гарантированно заканчивается этим результатом**: возможны protocol errors и `input_required`. Поэтому трактовка — «тип ответа относится к соответствующему типу запроса», а не «каждый вызов обязательно генерирует результат». Это не `in_topic`, не `realizes`, не `part_of`.
- `Tool Result → flows_to → Model` **ложно как безусловное**: в [политике `stop_on_first_tool`](https://openai.github.io/openai-agents-python/agents/) результат становится финальным ответом без нового обращения к модели, а `run_llm_again` возвращает его модели.

Итак, типовое отношение «ответ на запрос» может быть устойчивым, хотя фактическая доставка зависит от исполнения. Если оно понадобится для поиска по многим протоколам, его можно рассмотреть отдельно; **не добавлять только ради Runner**.

## 4. Оценка предложенных классов

| Кандидат | Новый вопрос, который восемь предикатов не решают | Проверка на данных | Вердикт |
| --- | --- | --- | --- |
| `depends_on` / более точный `requires_role` | Какие роли обязательно нужны для работы механизма? | Pipeline: Receiver/Exporter обязательны, Processor нет | **Перспективно**, но общий `depends_on` слишком неоднозначен; проверить ещё один независимый механизм |
| `provides` (ArchiMate Serving) | Кто предоставляет сервис/способность кому? | Между текущими 9 Collector Knowledge нет явно выделенного сервиса и потребителя, для которых пара доказана | **Отложить** до конкретного запроса и референтов |
| `consumes` (ArchiMate Access/Input) | Какие типы данных потребляет функция? | Универсальный Receiver не ограничен одним типом сигнала; конкретный OTLP traces pipeline — конфигурация | **Локальное описание** до появления устойчивой пары «функция — тип данных» |
| `produces` (ArchiMate Access/Output) | Какие типы артефактов формирует деятельность? | При `Tool Call → Tool Result` смешиваются запрос, операция и ответ; результат не обязан появиться на каждый вызов | **Не вводить** в виде такого ребра |
| `flows_to` (ArchiMate Flow) | Кто кому передаёт данные? | Receiver → Processor для A, Receiver → Exporter для B | **Конфигурационный маршрут**, таблица/Mermaid, а не глобальное ребро |
| `responds_to` / `result_of` | Какой тип ответа соответствует типу запроса? | Tool Result ↔ Tool Call, по контракту MCP | **Перспективно** при повторяемом спросе по протоколам; «ответ» не гарантируется для каждого вызова |
| `executes`, `realizes` | Кто исполняет Pipeline? Какой механизм реализует цикл? | Collector/Runner уже имеют подтверждённые рёбра | **Оставить существующие** |

`serving`, `access`, `flow`, `triggering` — **содержательно разные** отношения в ArchiMate, не синонимы «есть взаимодействие». Для нашей модели они уместны только при подтверждении двух именованных референтов, реального запроса и области истинности.

## 5. Что можно проверить в Obsidian без расширения схемы

Текущий K-Plex способен отфильтровать `part_of` и `executes`, но **не покажет обязательные роли**, потому что такой факт в YAML вообще не выражен. Текст Pipeline сообщает «processors optional», но это не машиночитаемый межузловой запрос.

Простая мысленная проекция без новых фактов в `main`:

```text
Состав (существующий part_of):
  Receiver ─┐
  Processor ├──► Pipeline
  Exporter ─┘

Обязательные роли (кандидат requires_role; НЕ YAML):
  Pipeline ──► Receiver   [не менее одного]
  Pipeline ──► Exporter   [не менее одного]

Маршрут данных (НЕ универсальный факт):
  A: Receiver → Processor → Exporter
  B: Receiver → Exporter
```

**Разные фильтры отвечают на разные вопросы.** Правило «все детали оставить в заметке» применимо к маршрутным условиям, но скрывает потенциально важные **устойчивые зависимости**, которые можно было бы запрашивать в масштабах графа.

## 6. Решение и критерий следующей итерации

- **P0.** Не создавать `flows_to` по соседству архитектурных ролей и не считать `part_of` обязательностью. Не смешивать типы сообщений и экземпляры их доставки.
- **P1.** Выделить две кандидатные категории для дальнейшей проверки: «обязательная роль/зависимость» и «ответное сообщение к запросу». Не фиксировать пока финальные имена `requires_role` / `responds_to`.
- **P1.** Проверить **по второму независимому примеру для каждой категории**, что предикат сохраняет один смысл и позволяет выполнить повторяемый межузловой запрос. Если нет — оставить таблицу в карточке.
- **P2.** Только после такого подтверждения подготовить отдельный ADR/изменение `rules/relations.md`, схемы и валидатора с двумя контрольными положительными и отрицательными примерами. До решения владельца никаких изменений Vault.
- **P3.** Позже проверить K-Plex на отборе реально добавленных типов рёбер. Сейчас дополнительный GUI-пилот не отвечает на семантический вопрос.

**Границы проверки:** source-first анализ текущих заметок и официальной документации. Исполнение двух конфигураций Collector и новый GUI-тест K-Plex не проводились; поддержка будущих предикатов валидатором не заявляется. Отчёт не меняет ни один Knowledge, YAML-ребро, ADR или правило.

### 7.1. Обязательная роль и соседние, но иные виды необходимости

**Контрольный положительный пример (Collector).** В обычном активном OpenTelemetry Collector Pipeline обязательно наличие хотя бы одного участника в роли приёмника и одного в роли экспортёра; последовательность processors может быть пустой. Канонические \`Receiver/Processor/Exporter → part_of → Pipeline\` показывают структурные роли одинаково и не отвечают на вопрос обязательности. Кандидат \`Pipeline → requires_role → Receiver/Exporter\` читался бы как *при работоспособном pipeline соответствующая роль должна быть занята хотя бы одним совместимым участником*. Источник — [Collector Architecture](https://opentelemetry.io/docs/collector/architecture/) и [конфигурация](https://opentelemetry.io/docs/collector/configuration/). Допускаются разные инстанции, их совместное использование между pipelines, connectors в соответствующих ролях и feature-gates; нельзя выводить обязательность *данного экземпляра*.

**Независимый пример №1 (Inspect AI Task) — строгую семантику не переносит.** Существуют \`Inspect AI Task\`, \`Inspect AI Dataset\`, \`Inspect AI Scorer\`. Описание Task типично соединяет dataset, solver и scorer, но [API Task](https://inspect.aisi.org.uk/reference/inspect_ai.html) допускает \`dataset=None\` или динамический \`SampleSource\`, использует solver \`generate()\` по умолчанию и допускает \`scorer=None\`. Нельзя без уточнения режима утверждать \`Task → requires_role → Dataset\` (не обязательно именно Knowledge Dataset) или \`Task → requires_role → Scorer\` (scorer необязателен). Обязательность конкретной реализации Solver также не доказана: есть default и override, а отдельного \`Inspect AI Solver\` Knowledge в \`main\` нет. **Результат:** механический перенос идеи «элементы рецепта = обязательные роли» ложен.

**Независимый пример №2 (MCP Tool Definition) — обязательная часть контракта, не роль исполнения.** В \`main\` уже есть \`MCP Tool Input Schema → part_of → MCP Tool Definition\` и \`MCP Tool Output Schema → part_of → MCP Tool Definition\`. [MCP Tools 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/server/tools) требует \`inputSchema\`, но \`outputSchema\` допускает отсутствие. Запрос «какие составные части обязательны?» действительно не решается одним \`part_of\`. Однако это **обязательность поля контракта**, не участника, выполняющего функцию. Нельзя называть обе семантики \`requires_role\` без потери точности. Информация уже компактно хранится в двух карточках.

**Контрпример границы (Temporal Replay).** \`Temporal Workflow Replay\` использует \`Temporal Workflow Event History\` для восстановления состояния. [Temporal Event History](https://docs.temporal.io/encyclopedia/event-history) подтверждает эту обязательную *информационную предпосылку*. Формулировка \`Replay → requires_role → Event History\` ошибочно превратила бы данные в исполнителя или структурный компонент. Это случай потенциального \`requires_input\`, а не подтверждение \`requires_role\`.

**Итог:** в \`main\` подтверждён только один независимый *механизм* для строгого \`requires_role\` (Collector). В двух дополнительных механизмах повторяется **необходимость с другой семантикой**. Общий \`depends_on\` или \`requires\` объединял бы обязательную роль, поле протокола и входные данные, не позволяя фильтром понять, *что именно необходимо*; вводить его на текущих данных не стоит.

**Типизация при возможном будущем введении \`requires_role\`:**
- Источник: Knowledge о системе/механизме или структуре, чья работоспособность рассматривается при явно оговорённом контракте; цель: существующий Knowledge, обозначающий **роль** участника (не конкретную настроенную инстанцию, сообщение, поле или артефакт).
- Направление: зависимый механизм \`→ requires_role →\` обязательная роль.
- Устойчивость: для **каждого допустимого работающего экземпляра в указанной области**, роль должна быть реализована, но не обязательно конкретным объектом.
- Не \`part_of\`: обязательность не следует из наличия компонента в составе. Не \`executes\`/\`realizes\`: нет утверждения, кто именно исполняет операцию или реализует абстракцию. Не \`in_topic\`/\`broader\`/\`specializes\`/\`schedules\`/\`manages\`: это другие вопросы.
- Запрос, который появился бы: «какие роли необходимы для работы X?»; цена: определять роль и область корректности для каждой пары. **На сегодня это кандидат, не основание добавлять поле.**

### 7.2. Ответное сообщение и корреляция

**Первый механизм (MCP).** Типовой успешный ответ на \`tools/call\` содержит результат выполнения инструмента; ошибки протокола передаются как JSON-RPC \`error\`, ошибки инструмента — как результат с \`isError\`, а новый протокол допускает \`input_required\`. [Спецификация MCP Tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools). \`Tool Result → responds_to → Tool Call\` описывал бы **соответствие типов в контракте успешного/обработанного вызова**, а не обещание ответа на каждый фактический вызов. Отдельно [JSON-RPC 2.0](https://www.jsonrpc.org/specification) требует совпадения \`id\` у запроса и ответа, кроме уведомлений, для которых ответ запрещён.

**Второй независимый механизм (OpenAI Agents SDK).** [Интерфейс Model](https://openai.github.io/openai-agents-python/ref/models/interface/) требует сохранять \`call_id\` у выходов инструментов для корреляции с их вызовами. [Runner](https://openai.github.io/openai-agents-python/running_agents/) исполняет запросы инструментов условно, а политика завершения может не инициировать следующий модельный turn. Связь «результат относится к вызову» **устойчива на типовом уровне**; фактическая доставка результата модели и успешное завершение — другие утверждения. Это подтверждение смысла в **другой реализации**, но не в **другой паре Knowledge**: опять \`Tool Result\` и \`Tool Call\`.

**Проверка повторяемости в текущем Vault.** \`MCP Tool Listing (tools/list)\` уже описывает собственные запрос и ответ **в одной карточке**; отдельного Knowledge типа \`tools/list result\` в \`main\` нет. Создавать его ради одного ребра противоречило бы текущему критерию необходимости. \`Inspect AI EvalLog\` — результат запуска оценки, а не протокольный ответ на \`Inspect AI Task\`; \`Temporal Workflow Event History\` — журнал, а не «ответ на Replay». Это отрицательные контрпримеры.

**Если рассматривать \`responds_to\` в будущем:** source — Knowledge типа ответного/результирующего **сообщения**, target — Knowledge типа запросного сообщения; направление \`response type → responds_to → request type\`; запрос: «какие ответные типы предусмотрены для этого запроса?». Экземплярная корреляция по \`id\`/\`call_id\` остаётся в протоколе/trace. Не \`produces\`: сообщение может не появиться; не \`part_of\` или \`realizes\`: нет композиции или реализации; остальные шесть предикатов отвечают на иные вопросы. **Семантика подтверждена двумя механизмами, окупаемость отдельного YAML-ребра в этом графе пока не подтверждена.**

### 7.3. Сводка решений

| Кандидат | Точная семантика | Пример | Новый межузловой запрос | Применимость на текущих Knowledge | Решение |
| --- | --- | --- | --- | --- | --- |
| \`requires_role\` | Для работоспособного X необходимо занять роль Y (≥1 совместимый участник) | Pipeline → Receiver / Exporter, не Processor | Какие роли необходимы X? | Только один точный функциональный срез; Inspect Task не даёт такого же доказательства | **P1: оставить кандидатом, пока не найден второй положительный механизм** |
| \`requires\` / \`depends_on\` | Необобщённая «зависимость» с разными основаниями | Pipeline/Receiver; Definition/Input Schema; Replay/Event History | Что вообще требуется X? | Широко, но без различения роли, контракта и входа | **P0: отклонить как слишком неоднозначный** |
| \`requires_input\` | Механизм требует определённые данные на входе | Temporal Replay → Event History | Что требуется на входе для X? | Одна точная пара, I/O уже описаны в карточке | **P2: оставить внутри Knowledge** |
| \`required_part\` | Контракт требует обязательный структурный элемент | MCP Definition → Input Schema, но не Output Schema | Какая часть обязательна? | Одна пара обязательной части, обе уже \`part_of\` | **P2: оставить в Knowledge** |
| \`responds_to\` | Тип ответа коррелирует с типом запроса по контракту | Tool Result → Tool Call (MCP и OpenAI SDK) | Какие типы ответа соответствуют запросу? | Две реализации, но единственная пара Knowledge | **P1: не вводить до второй независимой пары и реальной потребности в поиске** |
| \`flows_to\` / \`consumes\` / \`produces\` | Передача, использование или порождение данных | Receiver → Processor либо Exporter | Кто получает/производит конкретные данные? | Без конфигурации/политики часто меняется; нужны дополнительные параметры | **P0: не фиксировать как безусловные рёбра** |
| \`provides\` / \`references\` | Предоставляет capability / указывает на контекст | Кандидаты: service capability; Span Link → SpanContext | Кто предоставляет X? На что ссылается Y? | Ещё не найден повторяющийся запрос; \`Span Link\` описан в карточке | **P2: не вводить до проверки второй пары** |

**Финальное решение на текущем материале: новых предикатов добавлять в канонический словарь пока не следует.** Это результат проверки двух гипотез, а не утверждение, что восьми предикатов достаточно для любых будущих вопросов. Сильнейший кандидат — **строго типизированная обязательная роль**; \`responds_to\` концептуально корректен, но его польза для поиска в Vault пока низка. При появлении двух независимых положительных пар одного смысла решение можно пересмотреть без импорта полной метамодели.

### 7.4. Три проекции одного неизменённого графа

Ниже **полная совокупность относящихся к выбранному вопросу подтверждённых рёбер внутри рассматриваемых срезов**, не новые YAML-связи; остальные тематические соседи за пределами среза не перечисляются.

| Срез | Подтверждённые рёбра в \`main\` | Тематический фильтр | Структурный фильтр | Функциональный фильтр |
| --- | --- | --- | --- | --- |
| Collector/Pipeline | \`Collector → executes → Pipeline\`; \`Pipeline → part_of → Collector\`; \`Receiver/Processor/Exporter → part_of → Pipeline\` | Тема по внешним соседям; внутри среза \`in_topic\` нет | \`part_of\` показывает все три роли без обязательности | \`executes\` даёт исполнителя Pipeline, не маршрут |
| Runner/Inner Loop/Tool Call/Tool Result | \`Runner → realizes → Inner Loop\`; \`Tool Call/Tool Result → in_topic → Inner Loop\`; \`Inner Loop → in_topic → Lifecycle Orchestration\` | \`in_topic\` покажет два протокольных понятия в цикле | Нет \`part_of\` в этом срезе; тематическую связь нельзя считать составом | \`realizes\` связывает Runner с Inner Loop; условное продолжение — в карточке/сценарии |
| MCP Tool Definition/Input Schema/Output Schema/Tool Listing | \`Input Schema/Output Schema → part_of → Tool Definition\`; \`Tool Definition/Tool Listing → in_topic → Tool Description Discovery and Selection\` | Группировка по теме обнаружения | \`part_of\` показывает обе схемы, не их кратность и обязательность | Описания \`tools/list\`, поля и ответы читаются в Knowledge; дополнительных устойчивых функциональных рёбер в срезе нет |

**Что выводится из YAML:** тематика, состав, исполнитель Pipeline и реализация Inner Loop Runner. **Что читается из Knowledge:** обязательность receiver/exporter, необязательность processors/scorer/outputSchema, входы/выходы, обработка ошибок, корреляция call/result. **Что нельзя определить без контекста:** получатель определённой порции телеметрии, активный набор и порядок processors, наличие tool call, адресат tool output, число модельных turns и конкретная корреляция идентификаторов. Примеры условных маршрутов остаются в PR #28/#31 и в официальных конфигурациях, а не превращаются в глобальные рёбра.

**Оговорка о представлениях:** фильтр Obsidian/K-Plex отображает только *уже записанные* типы рёбер; локальный текст с «required» не превращается в фильтруемое ребро. Обязательная роль могла бы стать отдельной проекцией **только после** изменения словаря и появления обоснованных YAML-рёбер; этого не выполнено.

### 7.5. Приоритеты и минимальный следующий шаг

- **P0.** Зафиксировать границу «устойчивое типовое отношение / обязательная роль / входные данные / поле протокола / конфигурационный маршрут / событие исполнения»; не назначать \`part_of\` как «required» и не добавлять безусловный \`flows_to\`.
- **P1.** Не вводить ни одного нового предиката по результатам этой итерации. Уточнения для **будущего** обсуждения: \`part_of\` не означает required; \`executes\` не утверждает порядок вызовов; \`realizes\` не устанавливает информационный обмен; \`in_topic\` — авторская тематика, а не структурная принадлежность. Эти разъяснения не требуют сейчас редактирования \`rules/relations.md\`.
- **P1.** Если именно **поиск обязательных ролей** станет практической потребностью, выбрать *один* новый независимый механизм с уже существующими двумя Knowledge, подтвердить строгую семантику \`requires_role\` на официальном источнике и записать два ожидаемых запроса (включая отрицательный пример) **в отчёте**, до контракта.
- **P2.** Для корреляции запрос/ответ пока оставить \`call_id\`, виды результата и ошибки в Knowledge. Вернуться к \`responds_to\`, когда появится вторая *другая пара* узлов и повторяемый поиск.
- **P3.** Отложить GUI-проверку новых фильтров до реальных YAML-предикатов; сейчас она не проверяет семантику.

**Предел результата:** это source-first анализ официальных источников и фактических Knowledge из \`main\`; исполнение конфигураций, GUI-проверка и миграция рёбер не проводились. \`main\`, \`vault/\`, действующие отношения, схема, валидатор, Skill и ADR-001 не изменены.
