## Замечания по приоритетам

### P1 — Категории смешиваются с фасетами

\`asynchronous-execution\`, \`asynchronous-lifecycle\`, \`asynchronous-flow-control\` сейчас являются дочерними Category. Они также могут пониматься как независимые **concerns/аспекты** для фильтрации знаний. Контракт \`rules/schema.md\` вообще не содержит \`facets\`.

Это **не означает**, что все три категории ошибочны. Но необходимо определить критерий: Category — тематическая область/раздел навигации, facet — отдельное поперечное измерение отбора. Иначе \`broader\` со временем начнёт смешивать «более широкую область» и «другой аспект». Решение о фасетах должно предшествовать следующему масштабированию, с небольшим проверяемым примером, а не автоматической миграцией всех узлов.

### P1 — Технические пути отображаются пользователю как названия

YAML содержит точные пути вида \`"[[taxonomy/categories/asynchronous-execution]]"\`. Это надёжно разрешает ссылки и различает одинаковые имена Category/Knowledge, но Obsidian показывает технический путь.

Предлагается сохранять полный путь для однозначности и добавить display text:
\`"[[taxonomy/categories/asynchronous-execution|Asynchronous Execution]]"\`.

Такой синтаксис поддерживается Obsidian; **существующий валидатор его пока отклоняет**. Нужно обновить синтаксис, тесты и выполнить реальную UI-проверку на одном примере до массовой правки.

Источник: https://obsidian.md/help/links

### P1 — Представления не показывают типизированные Knowledge–Knowledge

\`vault/views/knowledge.base\` перечисляет \`name\`, \`kind\`, \`lifecycle\`, \`review_status\`, \`categories\`, но **не показывает \`specializes\`, \`part_of\`, \`realizes\`**. Поэтому для человека граф выглядит как набор тематически сгруппированных узлов, хотя два K–K ребра существуют.

Добавить отдельный \`vault/views/relations.base\` или минимальное представление с названными предикатами и типами рёбер. Core Graph показывает ссылки без их предметной семантики; GUI со специализированным плагином требует отдельного теста.

### P1 — Неустойчивость \`kind\` у части Knowledge

Нужна экспертная проверка, не автоматическое исправление:
- \`I/O-bound Work\`: \`kind: property\` — это скорее характеристика нагрузки/класс работ, чем самостоятельное свойство.
- \`Parallelism\`: \`kind: model\` — возможно, свойство исполнения; связь с \`Concurrent Programming\` спорна как универсальная тематическая классификация.
- \`Concurrency\`: \`kind: model\` — возможна более точная смысловая граница.
- \`Asynchronous Runtime\`: \`kind: technology\` — может означать архитектурную среду исполнения, а не конкретную технологию.

Эти замечания не доказывают ошибочность узлов. Они показывают, что 11-значный словарь \`kind\` нуждается в практической проверке на референтах.

### P2 — Гранулярность Coroutine и Suspension

\`Coroutine\` и \`Coroutine Suspension and Resumption\` могут быть двумя полезными знаниями (вычисление против механизма приостановки), но без объяснительного тела их независимые смысловые границы хранятся только в отчёте. Провести предметную проверку перед окончательным принятием, исключить ненужное дробление.

### P2 — Служебные статусы загромождают свойства

\`lifecycle: skeleton\` и \`review_status: proposed\` дублируются на каждом узле первого запуска. Они описывают **разные оси** (стадия содержания / принятие сущности), поэтому не следует удалять их автоматически. Предметный эффект пока нулевой, UI перегружен. На следующей итерации решить, нужно ли хранить обе оси в каждой заметке, либо вести статус партии в отчёте и показывать только существенные свойства в представлениях.

### P2 — Непроверенное покрытие и ограничение baseline

Отчёт правильно фиксирует 14/16 тем, но показатель — тематическое соответствие заголовков, не качество объяснения. \`B15: Error propagation\` и \`B16: Timeouts\` остались вне корпуса. Заявлять 87.5% полноты предметной области нельзя.

### P2 — Множественные родители \`broader\` не испытаны

Текущий граф — дерево из 5 категорий, несмотря на поддержку DAG в контракте. Генератор обоснованно не создал искусственную ромбовидную иерархию. Возможность нескольких родителей следует тестировать на **отдельной fixture**, а не искажать предметную модель ради визуального сценария.

## Проверка предметных K–K отношений

1. \`Cooperative Task Scheduling → specializes → Task Scheduling\`: **предварительно обосновано**. Документация Python подтверждает кооперативное планирование задач event loop. Смысл \`specializes\` соответствует «частный способ планирования».
   Источник: https://docs.python.org/3/library/asyncio-task.html
2. \`Python asyncio.TaskGroup → realizes → Structured Concurrency\`: **предварительно обосновано**. Официальная документация Python связывает \`TaskGroup\` со structured concurrency.
   Источник: https://docs.python.org/3/library/asyncio-task.html

Оба рёбра — предметные \`proposed\`, окончательное утверждение владельцем отдельно. Отсутствие \`part_of\` само по себе не дефект; агент сознательно не утверждал универсальность механизма event loop для любого async runtime.
