# Канонические направленные отношения v1

Рёбра записываются в Knowledge-источнике в формате `source → predicate → target`. Цель — существующий Knowledge. Обратные связи вычисляются; рёбра необязательны.

| Предикат | Смысл |
| --- | --- |
| `in_topic` | source рассматривается в теме target, по выбранному источнику; не означает наследование или композицию |
| `broader` | тема source уже темы target |
| `specializes` | source — частный вид target (`is-a`) |
| `part_of` | source — составная часть целого target |
| `realizes` | source — конкретная реализация абстракции target |
| `schedules` | source планирует исполнение target |
| `executes` | source выполняет / обеспечивает выполнение target |
| `manages` | source управляет жизненным циклом target |

## Применение

1. Если материал действительно выражает связь, добавь её в исходный Knowledge и укажи материал в `sources` этого Knowledge. **Не нужен отдельный реестр обоснований рёбер.**
2. Выбирай предикат по его смыслу: авторская рубрикация, `is-a`, `part-whole`, реализация и функция — разные отношения. Оглавление само по себе не доказывает `part_of` или `specializes`.
3. Если отношения не следует из источника или его тип непонятен, оставь Knowledge без этой связи.
4. Не создавай дубли тройки, самоссылки, записанные обратные рёбра и циклы `broader`, `specializes`, `part_of`.
5. Compass/K-Plex/Canvas визуализируют имеющиеся связи, не устанавливают новых фактов.

## Смысл отношения: минимальная проверка

Каждое ребро — самостоятельное предметное утверждение, а не способ сделать граф плотнее или разнообразнее. Перед записью проверь смысл пары **source, target**, а не только совпадение названий с рубрикой или наличием функции в продукте:

- **`in_topic`:** источник относит сущность к теме. Это нормальное отношение, не запасной вариант и не ошибка «недостаточной глубины».
- **`specializes` (`is-a`):** source обозначает **вид/подтип** того, что обозначает target. Экземпляр, продукт или реализация класса — не подтип; для `instance_of` у нас нет предиката. Название рубрики во множественном числе не делает её классом типов.
- **`part_of`:** source является **составной частью именно того целого**, которое обозначает target. Принадлежность к экосистеме, интеграция, взаимодействие сервисов или наличие возможности в продукте сами по себе не доказывают композицию.
- **`realizes`:** source действительно реализует названную target абстракцию/контракт. «Пример технологии в тематическом разделе» не равен реализации абстракции.
- **Функциональные предикаты:** назначай по подтверждённой ответственности исполнителя, планировщика или управляющего компонента, а не по общему отношению инструментов.

Контрольные примеры:

| Утверждение | Вердикт | Причина |
| --- | --- | --- |
| `Langfuse → in_topic → Tracing and Monitoring Platforms` | Корректно | ETCLOVG задаёт тематическую рубрику |
| `Langfuse → specializes → Tracing and Monitoring Platforms` | Некорректно | Конкретный продукт не является подтипом тематической рубрики |
| `OpenTelemetry GenAI Inference Span → specializes → OpenTelemetry Span` | Корректно | Специализированный вид span |
| `OpenTelemetry Collector Receiver → part_of → OpenTelemetry Collector Pipeline` | Корректно | Компонент pipeline |
| `Prometheus Alertmanager → part_of → Prometheus` | Некорректно | Alertmanager — отдельный сервис в экосистеме, а не часть Prometheus server |

Если точный смысл ребра не подтверждён источником, допустимо записать только обоснованную тематическую связь или оставить узел без связи. **Не устанавливай квоту на нетематические предикаты**, не создавай для проверки новый evidence-реестр или обязательный review.

## Существующая карта

В ETCLOVG из [Agent Harness Engineering: A Survey, Figure 4](https://picrew.github.io/LLM-Harness/main.pdf#page=8) зафиксированы 42 `in_topic` (7 направлений и 35 подразделов). Это тематическая группировка авторов, а не `part_of` или `specializes`.

Словарь из восьми предикатов остаётся закрытым. Добавление предиката — отдельное изменение схемы и валидатора; обычный Discovery его не требует.
