# Knowledge Graph Discovery — минимальная итерация

Назначение: из заданной темы получить небольшой, проверяемый прирост канонического графа `vault/` без дублирования существующих сущностей и без вымышленных связей.

## Вход и ограничения

- Вход: тема, цель исследования, границы `in/out`, источники (если указаны) и лимит новых Knowledge. Если лимит не задан, используй **не более 8 новых Knowledge за итерацию**.
- Широкую тему (например, «AI в бизнес-процессах») сначала ограничь одним предметным срезом; зафиксируй принятые границы и непокрытые разделы. Не заявляй полноту всей области.
- При отсутствии достаточного обоснования не записывай спорную сущность или связь: оставь её кандидатом в отчёте.
- Canvas, K-Plex, конфигурацию Obsidian и нормативную схему не изменяй. Не создавай новые типы Knowledge, предикаты или поля YAML без отдельного решения.

## Процедура

1. **Подготовка.** Работай из корня Git-репозитория. Прочитай `AGENTS.md`, `rules/discovery.md`, `rules/knowledge.md`, `rules/schema.md`, `rules/taxonomy.md`, `rules/relations.md`, `rules/validation.md`. Проверь текущую ветку, `git status` и существующие файлы. Если текущая ветка `main`, создай экспериментальную ветку. Не перезаписывай чужие незавершённые изменения.
2. **Scope.** Создай или используй brief конкретного среза в `experiments/<topic-slug>/brief.md`: цель, границы `in/out`, лимит, первичные источники, независимый перечень контрольных тем и ограничения уверенности. Для широкой темы выбери только один минимальный полезный срез и явно обозначь его как гипотезу.
3. **Inventory.** До записи файлов проверь все `vault/knowledge/entries/` и `vault/taxonomy/categories/`: названия, `aliases`, устойчивые `id` и совпадения предметного смысла. Переиспользуй существующий Knowledge, если это тот же референт. Не создавай «локальные копии» общего знания ради связности.
4. **Evidence.** По возможности опирайся на первичные источники. Различай общие концепции и конкретные реализации, только если их предметные границы отличаются. Для каждой предлагаемой связи установи `source → predicate → target`, смысл и источник. Допустимые предикаты и их точные значения бери только из текущего `rules/relations.md`.
5. **Запись минимального среза.** Создай максимум разрешённое число `vault/knowledge/entries/<slug>.md` с действительным UUIDv7 через `node tools/new-id.mjs`, `type: knowledge`, `name`, `review_status: proposed`, `lifecycle: skeleton`, нужными `categories`, предметно подтверждёнными отношениями и `sources`. Содержимое — только YAML frontmatter + H1 по `rules/schema.md`; объяснительные статьи не пиши. Новые Category — только при доказанной необходимости, в соответствии с `rules/taxonomy.md`.
6. **Граф.** Храни один прямой факт `source + predicate + target` в YAML исходного узла. Не дублируй обратные, транзитивные или выводимые связи. Не подменяй `part_of` тематической близостью, `specializes` — структурой, `realizes` — использованием. Допустимы Knowledge без предметных K–K рёбер, если они обоснованно привязаны к категории.
7. **Gate.** Запусти `node tools/validate.mjs` и `node --test tools/validate.test.mjs`; проверь `git diff --check`, изменённые файлы и количество добавленных узлов/рёбер. Если проверка не пройдена, исправь или остановись, не выдавая результат за PASS.
8. **Evidence & checkpoint.** Запиши `reports/<topic-slug>-discovery.md`: входной scope и контрольные темы, добавленные/переиспользованные Knowledge, точные новые рёбра с обоснованиями, источники, кандидаты и пробелы, результаты команд, число узлов и рёбер, ограничения, `independent semantic review: NOT_RUN` и `Obsidian/K-Plex GUI: NOT_RUN`, если проверки действительно не проводились. Сделай коммит только в экспериментальной ветке и сообщи его SHA.

## Результат итерации

- Небольшой прирост существующего канонического графа; все новые Knowledge имеют `proposed`.
- Воспроизводимый отчёт с решениями и неразрешёнными кандидатами.
- Статический результат проверок отдельно от семантического качества. **Static PASS не равен semantic PASS.**
- Предложение ровно одного следующего тематического среза по обнаруженным пробелам.

Не запускай независимое ревью под видом проверки самим генератором. Отдельные навыки enrichment/review добавляются только после проверки полезности данного сценария.
