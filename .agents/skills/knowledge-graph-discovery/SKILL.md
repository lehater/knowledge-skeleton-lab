# Knowledge Graph Discovery

Перед работой прочитай `AGENTS.md`, `rules/schema.md`, `rules/knowledge.md`, `rules/relations.md`, `rules/discovery.md`; восстанови текущую ветку и Knowledge из GitHub.

## Режимы

- `discover` (**обычный**): подобрать источник, извлечь знание, переиспользовать или добавить Knowledge, указать URL и при необходимости направленные отношения.
- `contract` (**только при явном запросе**): менять правила/Skill/проверки без изменения предметных Knowledge.
- `correct` (**по конкретной проблеме**): исправить обнаруженное неверное знание, дубль или отношение после просмотра источника и затронутых ссылок.

## Порядок режима `discover`

1. Выбери наиболее надёжный для задачи стандарт, официальную документацию или первичную публикацию; прочитай нужный материал.
2. Найди в имеющемся графе тот же референт по названию, aliases и смыслу. Переиспользуй UUID либо создай новый.
3. Перенеси короткое утверждение в Knowledge (`lifecycle: enriched`) и URL в `sources`. Если есть только термин — `skeleton`.
4. Добавь только те отношения, которые действительно соответствуют источнику и предикатам `rules/relations.md`. Не связывай узлы искусственно.
5. Запусти `node tools/validate.mjs`, `node --test tools/validate.test.mjs` и `git diff --check`; сохрани небольшой результат в ветке и PR.

**Граница среза:** после наполнения проверь только связанные с изменёнными Knowledge ранее существовавшие узлы. Тот же референт — переиспользуй и дополни; общая абстракция и реализация — разные Knowledge; соседний `skeleton` вне охвата не требует автоматического раскрытия. Если такой пробел мешает понять текущий срез, обогати его в пределах задачи или кратко отметь границу в описании PR. См. [правило повторного использования](../../../rules/discovery.md#граница-исследования-и-повторное-использование). Это часть обычного Discovery, без нового поля, полного аудита и обязательного review.

## Приоритет охвата: сначала вширь, затем вглубь

По умолчанию исследуй предметную область **сначала вширь на выбранном уровне**, затем углубляй отдельные ветви по инженерной необходимости.

1. **Определи охват** из текущей задачи, существующих Knowledge и структуры первоисточника: какие соседние подтемы и ключевые понятия ещё не раскрыты.
2. **Первым проходом покрой основные подтемы**: для каждой извлеки из прочитанных источников самостоятельные понятия, назначение, ключевые механизмы и интерфейсы. Переиспользуй существующие Knowledge. Не уходи глубоко в одну технологию, пока соседние существенные подтемы остаются только заголовками.
3. **Углубляй выборочно** там, где поверхностного описания недостаточно для решения инженерного вопроса, понимания важной границы, контракта, ограничения или риска.
4. **Останавливайся по полезности**, руководствуясь разделом ниже. Охват означает содержательное понимание темы, а не максимальное число узлов или формальную необходимость создавать Knowledge на каждое слово.

Если глубокий вопрос критичен для корректности или безопасности уже рассматриваемого понятия, реши его сразу; это исключение из порядка охвата, а не повод произвольно менять область исследования. Новые связи фиксируй при обнаружении, без квот на типы и количество отношений.

## Глубина исследования и критерий остановки

Исследуй **до глубины, необходимой для понимания и применения рассматриваемой технологии в текущей предметной задаче**. Глубина — не фиксированное число уровней и не цель сама по себе.

1. **Технология / система:** назначение, граница, ответственность и сценарии применения.
2. **Механизмы:** что обеспечивает поведение системы, какие ограничения и гарантии они задают.
3. **Состав и интерфейсы:** самостоятельные компоненты, операции, контракты и параметры, **если они влияют на выбор, интеграцию, безопасность, настройку или эксплуатацию**. Это ориентиры, а не обязательные уровни для каждого узла.
4. **Внутренние алгоритмы, структуры данных и исходный код** исследуй только при наличии конкретного вопроса, который невозможно разрешить на предыдущем уровне. Не углубляйся автоматически в зависимости соседних предметных областей.

**Остановись**, когда по источникам уже понятны назначение, ответственность, значимые входы/выходы или интерфейсы, ограничения и взаимодействия, достаточные для текущего инженерного вопроса; следующий уровень детализации не меняет решения. Если осталась конкретная неизвестность, углубляй только соответствующую ветвь.

Пример для Harness Engineering: `Sandbox → Linux namespaces / cgroup v2 / seccomp → типы namespaces, контроллеры, интерфейсы и параметры` обычно достаточно. Внутреннее устройство планировщика Linux, BPF-интерпретатора или функции ядра исследуются только для конкретной задачи, а не ради исчерпывающей декомпозиции.

**Отношения проверяй по смыслу:** фиксируй только подтверждённые источником связи, сверяя семантику пары узлов с `rules/relations.md`, включая различие между темой, подтипом, экземпляром, составной частью и реализацией. Не стремись заменить `in_topic` более «сильным» предикатом или увеличить число нетематических связей. Не дроби заметки на узлы ради количества и не создавай обязательного отчёта о достижении глубины.

Не создавай отдельный evidence-реестр, баллы доверия, обязательный независимый review или новый онтологический тип. Нет необходимости аудировать весь существующий граф при каждом пополнении. Не меняй `main` и не выполняй merge без решения владельца.
